# Glossary

Domain terms for Aseprite Agent. Code, docs and architecture reviews use these names.

**Bridge**: the Node process (`agent/bridge`) between agents and Aseprite. It serves MCP to agents (stdio for agent sessions, localhost HTTP for agents the chat panel starts) and talks to the extension over WebSocket.

**Extension**: the Aseprite Lua extension (`agent/extension`). `agent.lua` wires its modules: **Document Handlers** (`document_handlers.lua`, what the bridge can ask of Aseprite, with no transport) and **Bridge Connection** (`bridge_connection.lua`, session file, WebSocket, handshake, reconnects). File, shell and socket access stay in the entry scripts (`agent.lua`, and `headless_runner.lua` for the Headless runner), because Aseprite asks permission per script file. The Document Handlers use `pixels.lua` for hex colors, RGB images, pixel walking and base64, and `wire_params.lua` to check request params. Their **operation policy** comes from `protocol.json`: each request is a read, a write or a scoped write (and may need an active sprite); every write gets step capture, and a sub-agent's scope guard checks scoped writes and refuses the rest. Handler groups live in area files (`handlers_check.lua`, `handlers_color.lua`, `handlers_sprite.lua`, `handlers_apply.lua`). The **Document View** (`document_view.lua`) answers what the document looks like to the agent and the panel: layer ids and paths, get_state's `State` (sprite descriptions plus the user's **context**, `contextOf`: tool, brush, colors, zoom, active layer, frame, tag and cel, timeline range), the State block, the context line and `aseprite://` URIs; the State block and the context line are views of the same `contextOf`. The Chat Panel's draft (text, mentions, attachments, the `/` picker and skill chip) is the **Composer** (`composer.lua`): a pure module that turns Enter into one outcome (run a command, pick, tip, confirm, send).

**Session file**: `~/.aseprite-agent/session.json`, where the newest bridge publishes its port, token and path so the extension can find it. The same port answers `GET /status` (`{connected, aseprite}`, no token) for the Plugin's SessionStart hook, and `GET /files` (the open sprites' files, with the token) for the Headless runner.

**Wire Protocol**: the JSON-RPC messages between bridge and extension, defined once in `agent/extension/protocol.json` (version, requests with their param schemas and typed results, binary results, bridge methods with their param schemas, **shapes**, chat events). Both sides check their code against it, and the bridge rejects a different version at hello. **Wire types**: a base type (string, integer, layer, frames, bytes, ...) or a shape name (an object with those fields, e.g. `Attachment`, `Layer`, `State`; `"...": "Other"` includes Other's fields), with `[]` (list of) and `{}` (map of) suffixes and `?` for optional; unknown fields are errors, and `[]` and `{}` stand for each other (Lua writes an empty table as `[]`). **Receiver checks** (#96): each side checks what it receives, once, with the same rules and messages (`protocol.ts` and `wire_params.lua`), and errors name the method and the param path (`chat.send: 'attachments[0].path' must be a string`). The extension checks a request's params (`wire_params.lua`) before a handler runs; the bridge sends them unchecked after its tools' zod schemas. The bridge checks a bridge method's params (`checkBridgeParams`, in AsepriteLink before the handler) and a typed result as it arrives (`checkResult`; get_state's `State`, in AsepriteLink and HeadlessLink). The extension's check also resolves **layer references** (id or name) to layer ids and **frame specs** (`3`, `[1,3]`, `'2-4'`, `'all'`) to frame numbers in range, with one grammar shared by both sides. **Pixel bytes** (the `bytes` param type, e.g. `rgba`) travel as **binary requests**: the bridge's Document passes raw bytes, AsepriteLink sends the request with `binary: <length>` followed by one binary WebSocket frame holding every image, and the params point into it with `{offset, length}`; the Headless runner gets base64 instead, which the extension still accepts everywhere.

**Agent Provider**: one agent the chat panel can run (Claude Code, Codex). Each provider names its ACP agent package and how to pass the system prompt, and keeps a stream-json adapter (the CLI command plus a parser of its JSON output) as a fallback (`agent/bridge/src/providers`).

**ACP Runtime**: how the chat runs agents by default: the Agent Client Protocol, through `claude-agent-acp` and `codex-acp`. One long-lived agent process per provider, one ACP session per Conversation; a message is `session/prompt`, Stop is `session/cancel`, and after a bridge restart the Conversation continues with `session/load` (`agent/bridge/src/acp.ts`, mapped to chat events by `acp_mapper.ts`). `ASEPRITE_AGENT_RUNTIME=stream` uses the stream-json CLIs instead.
**Runtime seam**: how ChatRunner runs a turn (`agent/bridge/src/runtime.ts`): `start(turn, sink)`, `stop()`, with two adapters, the ACP runtime and the stream runtime. ChatRunner owns conversation keys (`claude`, `claude:dev`, ...), builds the agent's message from the parts the panel sends (prompt, state, changes, attachments, mode) and emits the turn's end; the panel sends its whole map of conversation ids and never computes keys.

**Plan**: the agent's checklist for the running turn (ACP `plan` updates), shown in the Chat Panel and updated in place.

**Permission request**: an ACP agent asking before it uses a tool that is not pre-approved. The Chat Panel shows the agent's options; no answer within two minutes rejects it. In Agent mode Claude has the shell and its to-do list (TodoWrite, shown as the Plan); the shell runs in its "Manual" permission mode (set with `session/set_mode`), so commands that change things ask; tests drive the round trip with a scripted agent (`ASEPRITE_AGENT_ACP_AGENT`, `agent/bridge/test/helpers/fake_acp_agent.mjs`).

**Conversation**: one chat thread with a provider, identified by the provider's own id (Claude session id, Codex thread id). The chat panel's Conversation module (`agent/extension/conversation.lua`) records its messages and steps and keeps the ids, so a conversation survives bridge restarts.

**Chat Panel**: the panel in Aseprite where the user types requests and sees the agent's steps.

**Tool**: an MCP tool the bridge offers agents (`get_state`, `execute_lua`, `snapshot`, ...). A tool is either an edit (changes the document) or a read. `get_context` is a view of `get_state` (#96, `contextOf` in `document.ts`): the user's selection and active layer, frame, tag and cel, with layer paths; there is no get_context wire request since protocol 41.

**Core tool set**: the tools an MCP client lists by default (#88), `CORE_TOOL_NAMES` in `agent/bridge/src/tool_sets.ts`, (#113: state, apply, Lua, pixels, snapshot, check, the timeline as text, the animation flow `motion_clip`, `inbetween`, `motion_check`, undo, the guide and the chat's own steps) plus the **meta tools** `find_tools` (search the rest, with each tool's inputs) and `call_tool` (run any allowed tool by name, its input checked against the tool's schema). The other tools are **deferred**: still in the Tool table and callable, but not listed, so every model call carries a much smaller tool list. Dispatch rather than dynamic registration, because the chat's HTTP endpoint is stateless. A skill's deferred `tools:` come with their signatures in its text (`skillToolsNote`, in the chat's skill context, `read_guide`, the MCP prompts and the plugin's skill files); the chat prompt does the same for the deferred tools the basics guide names. `ASEPRITE_AGENT_TOOLS=all` lists every tool.

**Apply** (tool and wire method): the whole change as data (#88), a list of ops (layers, pixels and shapes, cels, frames, tags, palette) run in order in one transaction, so one undo step (`agent/bridge/src/apply.ts`, `agent/extension/handlers_apply.lua`). The bridge checks the op shapes first; the extension runs every op in its own pcall, so every failing op is reported by its path (`ops[2]`), then rolls back when any failed or for a **dry run**, which therefore checks against the live sprite exactly. Pixel ops share write_pixels' grid code. Sub-agents may only use the cel and pixel ops.

**Tool table**: the single definition of every tool (`agent/bridge/src/tools.ts`): name, input, edit/read kind, step label and behaviour. MCP registration and chat labels come from it. Every tool lives in a `*_tools.ts` module (core, command, timeline and guide tools as well as the skill tools), listed once in the **tool module registry** (`tool_modules.ts`); the `Tool` interface, result helpers and the **tool context** are in `tool.ts`. A tool runs with `run(input, ctx)`: the context is the Aseprite requester plus the Saved Commands store and, for the main agent, the sub-agent runner, built once per MCP server (no globals). Inputs several tools share (frame specs, an image source, a palette by name) are defined once in `tool_inputs.ts`.

**Document module**: how skill tools see and change the active sprite (`agent/bridge/src/document.ts`): `info()` (size, frames and durations, layers with ids, tags, palette, selection, from `get_state`), frame specs, layer pixels, putting images or new sprites, and the color and sprite writes (colors, palette, color maps, mirrored frames, layer splits, slices, swatches), over the existing wire requests. Every write refreshes `info()`. Tools never write Lua for this; tests use an in-memory fake document (`fake_document.mjs`) that does what the Lua handlers do.

**State block**: the `<aseprite-state>` text sent with every chat message: sprite, palette, layers top to bottom with ids, tags, active layer/frame/cel and selections (`stateBlock()` in `document_view.lua`). It also lists which frames each layer has art in, the frame durations when they vary, and one line per Motion Clip (#113).

**Layer id**: `L` plus Aseprite's `Layer.id` (e.g. `L12`), stable for the session. Used in the state block, mentions and `layerById()`.

**Check**: the pixel-art check gate (`check` tool): mechanical rules (off-palette, orphan, semi-transparent, empty cels in a tag, flat or accidental frame durations, content outside the canvas, identical neighboring frames, the ground line jumping between frames) that return findings with coordinates and a fix. Layers that do not blend Normal (an Addition glow) are light layers: the per-pixel rules skip them and the result names them. Agents run it before saying they are done; the chat shows its result as a badge on the turn. In this fork the per-pixel rules use the **native pixel helpers** `Image:histogram()` and `Image:isolatedPixels()` (`src/app/script/image_class.cpp`); on a stock Aseprite they walk the pixels in Lua, with the same findings.
**Check expectations**: what the caller states the animation must hold, passed to `check` as `expect` and reported as errors whatever rules are selected: `layer_frames` (`{Weapon: "3-5"}`: the layer has art only in those frames and a non-empty cel in each) and `must_not_overlap` (`[["Weapon", "Head"]]`: the frames where both layers have a pixel with alpha 128 or more at the same place, with the count and sample coordinates). Layers by id or name; a group stands for its visible image layers; a linked cel counts in every frame it appears in (`handlers_check.lua`).

**Mention**: a reference to a document object typed in the chat with `@` (picker) and shown as a `@[Body]` token; sent to the agent as `Body (aseprite://layer/L12)`.

**aseprite:// URI**: the address of a document object, shared by mentions and the agent's citations: `aseprite://layer/L12`, `frame/3`, `tag/<name>`, `cel/L12:3`, `palette/5`, `slice/<name>`, `selection`. Links in replies select the object when clicked (`Uri` in `document_view.lua`).

**Turn controller**: the life of one reply in the Chat Panel (`turns.lua`): it starts the turn in the Conversation and Turn History, claims step captures for edit steps, finishes or fails it, and answers revert, restore and what changed since the last reply. Questions the panel asks the user (permissions, Developer apply and discard, revert anyway) go through the **Prompter** (`prompter.lua`): `app.alert` in the app, scripted answers in tests.

**Turn History**: where each agent reply sits in the sprite's undo history (`turn_history.lua`). It reverts and restores a whole reply and summarises what changed since the last reply (`<changes-since-your-last-reply>`, sent before the state block).

**Undo state id**: a never-reused id of an undo history state (this fork's `UndoState::id()`), read through `sprite.undoHistory.states` / `.current` and used with `sprite:undoTo(id)`.

**Step**: one row of an agent turn in the chat panel: a thought, a tool call with its result, or the reply.

**Script Panel**: a script dialog docked in the main window (`Dialog{ dockable = true }`), implemented by `ScriptPanel` in this fork.

**Review views**: ways of looking at more than one frame in a single image, offered by `snapshot`'s `view` (`agent/bridge/src/views.ts`), because a vision model sees only the first frame of a GIF. The **filmstrip** lays out a tag's or a range's frames in rows with their frame numbers; the **onion skin** draws a frame solid over its neighbors, earlier ones tinted red and later ones blue (wrapping around a tag); **compare** puts a reference layer (REF) beside the art without it (ART). The bridge builds them from plain per-frame and per-layer snapshots through the Document module, so they change nothing and need no extra wire request. The animate skill looks at the filmstrip before it reports.

**Step Capture**: before and after images of the request's frame (the site's sprite and frame, see Document-scoped request) for every write request (the operation policy's writes), with a diff (changed pixels in red over a faded frame), kept in memory in a ring buffer of 50 (`agent/extension/step_capture.lua`); each step records its chat and sprite, and a reply step claims every capture of its chat since the last one (merged only on the same sprite and frame). The Chat Panel attaches each capture to its edit step as thumbnails; the `diff_visual` tool compares the canvas with the last step or a named checkpoint.

**Attachment**: an image the user sends with a chat message so the agent can see it: the selection, the active layer or frame rendered to a PNG (upscaled to at most 512 px, `agent/extension/attachments.lua`), the clipboard image, or an image file in any format Aseprite opens. The bridge sends each as one ACP image block (`agent/bridge/src/attachments.ts`): PNG, JPEG, WebP and still GIF as they are; other formats, animations (as a numbered contact sheet with frame times), tiny and huge images converted with `aseprite -b --sheet` first.

**Chat Mode**: how much the agent may do in a turn (#24). **Agent** uses every tool; **Ask** and **Plan** connect the agent to the bridge's read-only MCP endpoint (`/mcp/ask`, read tools only), and Plan asks for a numbered plan that **Apply plan** carries out in Agent mode. Switching between Agent and the read-only modes restarts the ACP agent and loads the same session with the other endpoint.

**AI layer**: a layer named `AI: <task>` that holds content the agent generated, created above the source layer with `aiLayer(task, prompt)`; the request is stored in `layer.properties("aseprite-agent").prompt`.

**Variations**: candidate results for one task, built by the agent as layers `AI: <task> v<i>` in a group `AI variations: <task>` (`variationLayer(task, i)`) and shown with the `propose_variations` tool. The user keeps one (it becomes the AI layer) or discards them; each is one undo step (`agent/extension/variations.lua`).

**Skill**: a markdown file of techniques for the agent. Built-in skills live in `agent/skills/<name>/SKILL.md` (with `title`, `category`, `needs`: `image` or `selection`, `tools`); guide topics in `agent/guide`; user skills in `~/.aseprite-agent/skills/<name>.md` or `<name>/SKILL.md` with optional frontmatter (`name`, `description`, `triggers`, and like built-ins `title`, `category`, `needs`) and replace a built-in topic of the same name. A chat message that contains a trigger word brings the skill along (inlined when short, otherwise a hint to `read_guide` it); `/skill:name` forces one (`agent/bridge/src/guide.ts`).

**Brief**: the six decisions an open-ended request needs before drawing (size, palette, view, light, outline, destination), stated in one message as decisions, not questions; the agent asks only what truly blocks it and holds later steps to them (skill `agent/skills/brief/SKILL.md`, #78).

**Studio**: the orchestrator skill (`agent/skills/studio/SKILL.md`, #78). Its routing table maps a request to a **chain** of skills (e.g. `brief` → new sprite → draw → `shade-sprite` → `animate` → `review` → `export-game`); the chain becomes the turn's Plan, each skill is read with `read_guide` when its stage starts, and the turn ends with a **compromise report** (what was cut or approximated, and why). Every built-in skill ends with a **Then line** (`Then: ` and the usual next skill in backticks), which `bridge/test/skill_then.test.mjs` checks against the catalog.

**Skill eval**: a check that a built-in skill's deterministic tools do what the skill promises (`agent/tests/skills/<name>.eval.mjs`): a fixture sprite on the fake document, the tool steps, and assertions. `npm test` runs one per skill and fails when a skill has none; skills whose tools all run inside Aseprite or call an agent are skipped with a reason, naming the Lua test that covers them when there is one. `run_live.mjs --evals` runs the same evals against the real Aseprite (`agent/tests/eval_live.mjs`: the fixture is rebuilt as Lua, the checks read `get_state`/`snapshot`), with no model.

**Contract suite**: request scenarios (fixture, wire requests, expected results, errors and pixels) in `agent/tests/contract/*.json`, replayed against both the fake document (`contract.test.mjs`) and the real Lua handlers (`contract_test.lua`), so the fake cannot drift from Aseprite. Both runners also check every typed result (get_state's `State`) against `protocol.json`, and `bridgeMethod` steps check bridge-method params with both sides' checkers (`contract/wire.json`). What the fake does not model it refuses with "fake document: … not supported".

**Benchmark**: a fixed, multi-step task for one skill that is judged on the art as well as on what it did (`agent/tests/bench/<name>.json`, run by `agent/tests/run_bench.mjs`): a fixture (Lua that builds the starting sprite with an explicit palette), two or more prompts, and pass/fail criteria checked through the tools. A run is stored as `generation.yaml` plus a filmstrip, the last frame and the `.aseprite` file in the bench folder's `runs/<date>-<provider>/<name>/`, and scored blind on a 5-axis 0-4 rubric (`RUBRIC.md`) by the provider that did not draw it. Unlike a **Skill eval** it uses a model; unlike a **Live test** it scores quality, not only that the skill ran.

**Live test**: a test that drives the real Aseprite and a real agent (`agent/tests/*_live.mjs`, run by `run_live.mjs`). The summary splits **tool** results (evals, deterministic) from **agent** results; hard checks prove the skill ran and its result is sound, **soft checks** (`soft()`) score the model's choices (names, thresholds, timing) and never fail the run.

**Lua-tests stamp**: a hash of the extension and `protocol.json`, written by a full passing `run_lua_tests.sh` (a gitignored file in `agent/tests`); `npm test` warns when the extension changed since, and fails with `ASEPRITE_AGENT_REQUIRE_LUA=1` (the pre-push hook, `agent/tools/pre-push.sh`). Generated files are rebuilt by `npm run gen` and checked by `npm run gen:check`.

**Saved Command**: Lua the agent wrote and saved with `save_command`, kept in `~/.aseprite-agent/commands` (`commands.json` plus `<name>.lua`, a git repository with a commit per change). It runs as one undo step with an `args` table, from **My Commands** in the menu, from `/name args` in the chat (no agent turn), or through `run_saved_command` (`agent/bridge/src/saved_commands.ts`, `agent/extension/saved_commands.lua`).

**Timeline text**: the sprite's timeline as lines of text (`frames N`, `fps N`, `frame A-B duration Nms`, `tag NAME A-B direction [repeat=N]`, `layer NAME link|unlink A-B`). Frames, durations and tags are declarative (unlisted tags are removed); link lines are actions. `get_timeline_text` reads it and `apply_timeline_text` applies it in one undo step or returns a plan (`agent/extension/timeline_text.lua`).

**ase**: the command-line form of the tools (`agent/bridge/src/cli.ts`). Live mode starts a short-lived bridge that the extension connects to; file mode runs `aseprite -b` on a file; headless mode (`--headless`) runs many files through one Headless runner.

**Headless runner**: one long-lived `aseprite -b` running `agent/extension/headless_runner.lua`, which loads the same Document Handlers and `protocol.json` as the live extension and keeps documents in memory between requests. It reads JSON lines on stdin (`{id, method, params}`) and writes marked reply lines on stdout (`{id, result|error, binary?}`, binary as base64); besides the protocol requests it answers `open`, `close` and `shutdown`. The bridge side is `HeadlessLink` (`agent/bridge/src/headless.ts`), an AsepriteRequester, so the tools run on it unchanged. It is chosen only explicitly (`ase --headless`, `ASEPRITE_AGENT_MODE=headless`), never as a fallback, and refuses files the live window has open, which it learns from the newest bridge's token-protected `GET /files`.

**Plugin**: the Claude Code plugin in `agent/claude-plugin` (marketplace at the repository root): the `aseprite` MCP server, started by a launcher that finds the bridge through `~/.aseprite-agent/bridge.json`, the guide topics as skills, and two hooks: SessionStart asks the bridge's `GET /status` whether Aseprite is connected, and PostToolUse reminds the agent once per session, after an edit-kind tool, to look before it is done (the same reminder ends the chat's system prompt, `bridge/src/look.ts`). Skills, `hooks.json` and the hook's tool list are generated by `npm run gen`.

**Developer mode**: a Chat Mode in which the agent edits this fork with its normal coding tools in a **developer worktree** of its own (`~/.aseprite-agent/dev/worktrees/`, branch `dev/<date>-<slug>`, state in `~/.aseprite-agent/dev/state.json`), so the user's checkout never changes until they apply the work (`agent/bridge/src/developer.ts`). Rebuild & Relaunch first **applies**: it fast-forwards the user's branch to the agent's commits, refusing while the worktree has uncommitted changes, the checkout has changes to tracked files or is on another branch, or the branch moved (the agent rebases then). Then it runs `ninja aseprite` when non-extension files changed, sends build errors back to the agent, saves open sprites and the conversation, and restarts Aseprite. Discard stashes the agent's uncommitted changes, removes the worktree (the dev branch keeps its commits), and after an apply resets the user's branch to where it was, only while nothing changed since.

**Sub-agent**: an agent started by the lead agent's `spawn_agents` tool for one part of a multi-frame job, scoped to some frames (and optionally layers). Up to four run at once (`agent/bridge/src/subagents.ts`); each has its own MCP endpoint (`/mcp/scope/<id>`) that adds its scope to every request, and the extension's scope guard (`agent/extension/scope_guard.lua`) undoes any step that changes something outside it, on the request's own sprite (`sprite:undoTo`, also when that sprite isn't the active tab), and highlights the scope's frames in the timeline when that sprite is on screen. Its steps appear in the panel labeled with the scope.

**Critic**: a fresh agent that judges the art without having seen the conversation or the brief (#76). The `critique` tool starts one through the same provider runner as `spawn_agents` (`SubAgents.open`), on the read-only critics' endpoint (`/mcp/critic`: read tools only, no `critique`, `ab_compare` or `spawn_agents`), and gives it only snapshot or filmstrip images, a sprite state summary, the **Rules** index and an optional one-line "what this is". It must reply in strict JSON (retried once when it does not parse): a **cold read** (what the picture shows to a stranger), a 0-10 score and findings tagged BLOCKING, WORTH FIXING or NOTE, each citing a `rule:<id>`; ids missing from the rules index are flagged. Work ships at 7/10 or better with nothing BLOCKING (`agent/bridge/src/critic.ts`, skill `agent/skills/review/SKILL.md`).

**Blind A/B**: `ab_compare`, the gate a fix round must pass (#76): a fresh **Critic** sees two versions in one image, labelled A and B in a coin-flipped order the bridge records and the caller only learns with the verdict, and picks the better one. With a checkpoint the versions are the canvas `diff_visual save` kept and the canvas now, and the **fix guard** runs first: a fix that changed more than 25% of a layer's opaque pixels (beyond 8 px) since the checkpoint is a redraw, and the round is refused. `diff_visual save` also keeps a per-layer copy in the bridge for this (`agent/bridge/src/critic.ts`).

**Skill Catalog**: guide topics, built-in skills and user skills in one list (user skills override by name), served to agents by `list_skills`/`read_guide`, to the panel by `skills.list`, and to any MCP client as prompts (one per built-in or user skill, named like it, with an optional `request` argument) and `skill://<name>` resources (`agent/bridge/src/skill_mcp.ts`, `agent/docs/mcp-clients.md`); the read-only `/mcp/ask` endpoint has the resources but no prompts. Typing `/` in the chat shows matching skills and saved commands over the bottom of the log; Up/Down move the highlight and Enter or Tab picks it (keys reach Lua through the fork's `dlg:textedit{ onkeydown }`). A picked skill becomes a **skill chip** above the prompt and is sent as `/skill:name` in front of the next message (`agent/bridge/src/guide.ts`, `chat_panel.lua`).

**Known palettes**: the palettes `palette_from_image` compares against, `list_palettes` lists and `remap_to_palette` (and every `palette` input) accepts by name: the user's in `~/.aseprite-agent/palettes` (`.gpl`/`.hex`), the ones Aseprite ships (`data/extensions/*` `.gpl` files), and **Lospec palettes**, fetched by slug from Lospec's palette API on first use and cached with their name, author and URL in `~/.aseprite-agent/palettes/lospec/<slug>.json`; the credit is shown wherever one is used. Resolution order: `lospec:<slug>` goes to Lospec only; else the user's, then Aseprite's by name (case, spaces and dashes ignored); then an alias (`gameboy`, `nes`, `db32`, `endesga-32`, ...: Aseprite's copy when installed, else its Lospec slug); then cached Lospec palettes; then Lospec by slug. None are bundled by the agent (`agent/bridge/src/palettes.ts`).

**Tone**: a source's pixel-weighted OKLab statistics (lightness, saturation, contrast, warmth) used to compare and match sprites; the color math lives in `agent/bridge/src/color.ts`, and the extension only reads colors (`collect_colors`) and applies color maps (`apply_color_map`).

**Pixel grid**: a region of one layer as text, one key per pixel separated by spaces, with a legend of key -> hex (#74). `read_pixels` writes it and `write_pixels` reads it back in the same format: in indexed sprites a number is that palette entry (never the transparent index), in RGB sprites keys come from the read's legend, `#rrggbb` is that color, `.` is transparent and `-` leaves a pixel unchanged (read uses it outside the canvas). Ragged rows and unknown keys are refused with their row and column, never padded. The bridge checks the grid (`bridge/src/pixel_text.ts`) and the extension writes it (`write_pixels` in `document_handlers.lua`, a scoped write) in one undo step; the cel keeps its position and grows to cover painted pixels. Adapted from aseprite-ai-artist's PixelGrid (MIT).

**Rules** (pixel-art knowledge base): numeric craft rules by subject in `agent/guide/rules/<chapter>.md` (#77): `animation`, `characters`, `tiles`, `isometric`, `vfx`, `ui`. Each chapter has an id on its H1 (`# Animation timing {#anim}`) and rule ids on its H2/H3 headings (`### Walk {#anim.timing.walk}`); a rule is its heading's section. Skills and guide topics cite a rule as `` `rule:<id>` `` instead of restating it. Each chapter ends with Mistakes, Review and Templates: ```` ```grid ```` blocks of a `Legend:` line and rows in the **Pixel grid** format, ready for `write_pixels`. Served on demand by `read_guide` (`rules`, `rules/<chapter>`, a rule id), listed at the end of `list_skills`, and as MCP resources `rules://<chapter>` (`agent/bridge/src/rules.ts`); they are not skills, so no trigger inlines them. The plugin carries them as files of `aseprite-pixel-art`. Adapted from aseprite-ai-artist's `rules/` (MIT, `agent/guide/rules/CREDITS.md`).

**Pixel snap**: rebuilding upscaled or AI-generated "pixel art" at its native size (#37). The grid is the cell size and offset whose boundaries carry the most color change against chance (fractional cells allowed, small noisy changes ignored); each cell takes its dominant color (`agent/bridge/src/pixel_grid.ts`).

**Sheet import**: slicing a sprite sheet image into a new animated sprite (#41): by a grid (cell size from the gutters between sprites, margin keeping boundaries in gutters), by the sprites on it (8-connected shapes on a transparent or key-color background, nearby specks merged, reading order), or by an atlas JSON; frames are aligned bottom-center by default (`agent/bridge/src/sheet.ts`).

**Concept**: designing before drawing (#79): the concept skill writes an art spec and a prompt for an image model the user already has (a concept sheet of views, or a storyboard with one panel per frame, the layout stated so it can be sliced), generated with the **image generator** (`generate_image`, Codex's image generation on the user's Codex plan, only after the user allows it in the panel, #102) or brought by the user, or skipped. A storyboard's panels go onto a hidden, locked `AI: Reference` layer, one panel per frame (`storyboard_to_frames`, optionally with an editable `AI: Draft` of N colors to rework), the agent draws on its own layer and fixes the largest **mismatch regions** (areas where only the reference or only the art has shape, by silhouette). The image guides proportion and placement; a draft is where the drawing starts, never the finished pixels (`agent/bridge/src/concept.ts`, `image_gen.ts`, `concept_tools.ts`, skill `agent/skills/concept/SKILL.md`).

**Motion Clip**: the intended motion as data (#109, `agent/bridge/src/motion_clip.ts`), in the sprite's **motion store** (sprite property aseprite-agent "motion", versioned JSON). A **clip** per tag: kind (walk, run, idle, cycle, action), facing, loop, keys with their poses and holds, contacts, root travel, **followers** (a part that lags another, in frames), the walk's near limbs and the **stage** (none, keys, inbetweens, done); its frames are tag-relative. A **rig** per character: part layers with parents, and each part's joint and end in sprite pixels at a base frame (set, imported, or derived from pixels as a suggestion). The `motion_clip` tool plans, rigs and moves the stages; in the keys stage the extension's motion gate (`motion_gate.lua`) undoes any edit to a non-key frame of the tag.

**Inbetweener**: the `inbetween` tool (#110, `agent/bridge/src/inbetween.ts`): the frames between two keys made from the keys. Each part layer's move between them is solved as a rigid turn and shift (relative to its parent's), the turn's fixed point is the part's **joint**, and each in-between samples the move at the frame's elapsed time with an easing, so parts travel on arcs about their joints, keep their length and colors, and followers lag. Keys are never written.

**ComfyUI workflow**: a ComfyUI graph the user saved for the agent (#112, `agent/bridge/src/comfy.ts`, `agent/docs/comfyui.md`): an API-format JSON plus a **manifest** that names its params (a node's input; image params take a file the agent uploads) and its outputs by role (`image`, `pose`, `mask:<part>`, `depth`, `frames`). `comfy_run` runs one as a job over a transport (HTTP and the WebSocket; a fake in tests) and returns a **pose bundle**: the run's files by role in the session folder.

**Pose import**: `poses_to_frames` (#112, `agent/bridge/src/pose_import.ts`): key poses from files as frames of one animation, all with one anchor (the hips from OpenPose keypoints, else the feet), one crop and pixel grid, and one palette, so they don't jitter against each other. Keypoints become **landmarks** on the clip's keys; masks cut the poses into part layers and give the rig its parts.

**Motion analysis**: measuring how an animation moves (#111, `agent/bridge/src/motion_analysis.ts`): a **track** per part (its layer) and for the whole figure, with each frame's area, bounds, centroid, top and feet, and the metrics drawn from them: spacing, arcs, volume drift, **boiling** (pixels inside the shape that change color and change back), the ground row, foot slide, the loop seam and flat timing. `motion_check` reports it, `motion_clip done` refuses on its errors, `snapshot` `view: "trails"` draws the tracks over the ghosted frames, critics and the bench judge see that view, and benchmarks can require it (`motion_check` criterion).

**Pixel spec**: the decisions read from a concept, as JSON in target pixels (#79): canvas, the source and its panel grid, per frame the silhouette bounds `[x0, y0, x1, y1]`, center and landmarks (top and feet measured; eyes, hands, a weapon tip filled in by the agent), palette roles and deliberate deviations. `concept_spec` measures the skeleton; `pixel_spec` stores it in the sprite property aseprite-agent "concept.spec" (get_state's `pixelSpec`) for later steps and review.

**Style summary**: how a sprite is built (#40): size, colors, shading ramps and their steps, outline (one dark color, selout, or none) and dithering, with rules for drawing new art in that style (`agent/bridge/src/style.ts`). Recreating from a reference works only from images the user attaches, and says that recreated game art is for study and personal use.

**Ramp**: a pixel-art color ramp through a base color, dark to light, with shadows turning cool and highlights warm (`make_ramp`, `agent/bridge/src/shading.ts`). **Auto-shading** gives each flat color a short ramp and picks a step per pixel from the shape's distance field lit from a direction; **selout** outlines use a darker shade of the color each outline pixel borders.

**RotSprite transform**: rotating or scaling pixel art without blending: upscale x8 with Scale2x, sample through the inverse transform, and when an axis shrinks take the most common color in each pixel's footprint so thin lines survive (`agent/bridge/src/animation.ts`). Used by `transform_layer` (a part moved, turned, scaled or squashed in given frames, or swept along an eased arc) and `inbetween` (#110: each part's rigid move between two keys about its joint).

**Directions**: a character's facings as tags named by compass direction (`walk_S`, `E`, `idle-north`; S faces the viewer, E faces right). `direction_plan` lists what exists, what mirrors (E↔W, NE↔NW, SE↔SW) and what must be drawn; `mirror_direction` copies a tag flipped as the opposite direction (`agent/bridge/src/directions.ts`).

**Autotile set**: terrain tiles for every neighbor combination (47-tile blob, or 16 sides-only), composed from a 5-tile template (island, vertical, horizontal, fill, inner): each tile's four quarters are picked by its neighbors. Exported with neighbor masks as a Godot 4 TileSet (terrain peering bits), a Tiled wang set and JSON (`agent/bridge/src/tiles.ts`).

**Palette swap**: a recolored variant that maps whole ramps by position (dark to dark, light to light) so shading survives (`palette_swap`); for shaders, an index map (palette index per pixel) plus a lookup table with a row per variant (`export_palette_lut`, `agent/bridge/src/dither.ts`). **Ordered dithering** mixes two palette colors with a Bayer or checker pattern by how far a pixel sits between them.

**Normal map**: per-pixel surface directions for 2D lighting, made from a height field (a rounded bevel of the silhouette, the colors' lightness, or a grayscale height layer), quantized to a few tilt steps for a pixel look, in OpenGL (green up) or DirectX convention; kept on a hidden 'AI: normal <layer>' layer (`agent/bridge/src/normals.ts`).

**Emission and specular masks**: grayscale layers beside a normal map (hidden `AI: emission <layer>`, `AI: specular <layer>`): where the sprite glows regardless of light, and how shiny each pixel is, in a few gray steps (`agent/bridge/src/masks.ts`).

**Sub-pixel motion**: moving a drawing by a fraction of a pixel per frame by changing edge shades (sampled between pixels, snapped to the palette) instead of moving pixels, so slow moves in small sprites don't jump.

**Engine export**: frames packed into a grid sheet (trimmed with their offsets kept, padded and extruded against bleeding) plus metadata per engine: a Godot 4 SpriteFrames, a Unity .png.meta with slices and pivots, Phaser atlas and animations, a Tiled .tsx, and Aseprite's JSON hash; a normal layer gets a matching `_n` sheet (`agent/bridge/src/export.ts`). Effects: see FX export.

**Pixel text and UI**: text drawn from Aseprite's bitmap fonts (`aseprite` 7 px, `mini` 5 px; CC BY 4.0), parsed like Aseprite's sprite-sheet fonts; UI panels and buttons with a border, highlight, shadow and rounded corners, a 9-patch slice for stretching, button states as tagged frames, colors snapped to the palette (`agent/bridge/src/ui.ts`).

**Voxel render**: a MagicaVoxel model (or layers stacked as height slices) drawn as 2:1 isometric pixel art, each voxel a 4x4 block with three shades of its material (lit top, mid left, dark right), back to front, in 90-degree turns (`agent/bridge/src/voxels.ts`).

**Model render**: a 3D model (glTF/GLB or OBJ) drawn by the bridge's own software renderer at the sprite's final size: orthographic, z-buffered, sampled at pixel centers with no anti-aliasing, lit in a few toon bands, with one scale and ground line shared by every direction and frame (`agent/bridge/src/model3d.ts`).

**Pixel FX engine**: renders game effects (hit sparks, loops, explosions) as pixel-art frames (`agent/bridge/src/fx/index.ts`). `renderFx(effect, options, { fps, seed, palette })` steps an effect module on a fixed 120 Hz clock and returns baked frames, the light buffer as `glow`, the origin and size, the duration and whether it loops. The engine is pixelfx's core, vendored as-is (`agent/bridge/src/fx/vendor`); its license, credits and local edits are in `agent/bridge/src/fx/NOTICE.md`.

**FX library**: the curated pixelfx effects the agent can use (`agent/bridge/src/fx/library.ts`): about 40 impacts, melee slashes, explosions, lightning, arcane, holy and fire one-shots and loops, each vendored as-is under `agent/bridge/src/fx/vendor/effects/<category>/` and cataloged from its own meta (id, title, category, tags, loop or one-shot, duration, size, origin, fps, default palette, options) plus a default **anchor**: `center` (add_fx's x, y is the visual centre, the alpha-weighted centroid of the busiest frame: hits, slashes, bolts) or `ground` (x, y is pixelfx's origin, the ground point: fires, pillars, circles, explosions on the floor), derived from category and tags with a few hand-listed (`defaultAnchor`). Tools (`fx_tools.ts`): `list_fx`, `preview_fx` (a numbered contact sheet), `add_fx` (anchored by `fxAnchorPoint`, the effect's colors appended to the sprite palette in the same request (an indexed sprite past 256 entries snaps instead); onto `AI: fx <id>` layers, the glow on `AI: fx <id> glow` with Addition blend, sprite frames sampled at their start times, frames added past the end, one `put_images` request so one undo step) and `new_fx_sprite`.

**FX overlay**: a library effect timed onto a character's animation by `fx_overlay` (`agent/bridge/src/fx_timing_tools.ts`): the range is a tag or the frames from a start frame; `hit_frame` puts the effect's **impact** (its first pixelfx act hit for melee effects, else its busiest frame, `fxImpact`) on that frame's first moment. `overlayPlan` maps frames to effect times: **resample** shows the effect at each frame's start time and adds no frames; **retime** splits each frame the effect is on into parts of about one effect frame whose durations add up to the original, inserting frames whose cels are linked to the frame they split. A one-shot that outlasts the range is cut (default with a tag) or extended by linked frames after it (default with a start frame). `anchor_layer` places it at that layer's opaque bounds in the hit frame (centre, or bottom centre for a ground anchor; melee defaults to ground) and keeps it there. Placement (render at the planned times, anchor, cut, glow, palette, FX record with its `render` overrides) is the FX domain module's `planPlacement`, as for `add_fx`; writes go through `put_images`' `insert` and `durations` in one request. `preview: true` (also on `add_fx`) is a **context preview**: the same placement drawn over the sprite's frames (inserted frames show the frame they split, `originalFrame`), nothing written.

**Hit-stop**: a freeze on the contact frame of an attack, made by `hit_stop` (`agent/bridge/src/fx_timing_tools.ts`, `hitStopPlan`): the contact pose holds exactly `freeze_ms` longer. A shake spends `shake.ms` of that freeze on frames inserted after the contact frame, whose cels on the shaken layers are copies moved sideways by `amp` px decaying to 0 (the other layers link to the contact cel); the contact frame keeps the rest. `flash_layer` turns one layer white in the contact frame. The hit is recorded in the sprite property `aseprite-agent` `fx.hits` (`{ frame, freezeMs, shakeMs?, amp? }`, moved by later inserts; `get_state`'s `fxHits`, `SpriteInfo.hits`) for exporters. Its wire params and parsing are `hitWire` and `parseHits` in `agent/bridge/src/fx/record.ts`.

**FX record**: what export and `check_fx` need about an effect, written by every placing tool (`add_fx`, `fx_overlay`, `fx_from_recipe`, `new_fx_sprite`, `fluid_fx`, `fx_pipeline`) in the same request as the effect (`put_images`' or `create_animation`'s `fx`): the layer property `aseprite-agent` `fx` = `{ id, x, y, fps, loop, windupMs, recipe?, render? }` on the effect's layer (`AI: fx <id>`, or the glow layer when the color layer is empty; a new effect sprite's one layer). x, y is the effect's **origin** (pixelfx's ground point) in sprite pixels; **windup** is the ms from the effect's start to its impact (`fxImpact`). The id says what made it: a library id, `recipe:<name>` (the recipe's JSON in `recipe`), `fluid:<preset>` (`fluid_fx`'s settings in `render`, a 'sprite' ramp stored resolved) or `pipeline:<name>` (the pipeline's JSON in `recipe`, its source resolved); `render` of a library effect or recipe holds the settings that differ from its defaults (seed, flip, angle, options, palette, light). A layer property rather than a sprite one, so several effects can share a sprite and deleting the layer drops its record. Reported as `get_state`'s layer `fx`, `LayerInfo.fx`. **FX domain module** (#97): one owner in `agent/bridge/src/fx/`: `record.ts` names effect layers (`aiLayer`, `fxBase`, `glowBase`, `freeLayerName`, `isFxLayerName`, `isFxGlowName`), builds, sends and parses records and hits (`buildRecord`, `recordWire`, `parseRecord`, `hitWire`, `parseHits`; records missing recipe, render or windup read as before) and owns the render settings (`effectOptions`, `renderRecord`, `fxCanvas`); `place.ts` owns placement (`fxSchedule`, `placed`, `fxAnchorPoint`, `fxImpact`, `fxPalette`, `planPlacement`, `writePlacement`, `previewPlacement`); `render_record.ts` re-renders any record (`rerender`, `recordedEffect`, `fluidSettings`). The extension stores the record as given (`handlers_sprite.lua` checks its fields' types; `document_view.lua` copies it back as stored, `fxRecordOf`, `fxHitsOf`; its fields on the wire are protocol.json's `FxRecord` and `Hit` shapes).

**FX recipe**: an effect described as JSON instead of code (`agent/bridge/src/fx/recipe.ts`, tool `fx_from_recipe` in `fx_recipe_tools.ts`): name, size, origin, fps, duration, loop, seed, a palette ramp (dark to bright), an optional floor and anchor, and **phases** (charge, flash, burst, linger, decay), each a time window [start, end) with emitters (one of the core's 12 particle kinds, count, speed, angle and spread, life, delay, over, size, color, extra gravity and drag), lights, rings, bands (rings on the floor plane) and shapes (disc, glow). `recipeSchema` (zod) checks it with limits (size 256, count 400 an emitter and 1200 in all, 6 s) and messages by path; `compileRecipe` turns it into an effect module (meta + create) over the vendored core's `Particles`, `Lights`, `band` and painter, so `renderFx` and the placing tools take it as a library entry (`recipeEntry`, id `recipe:<name>`). Each cycle is a **run** (a sim and lights spawned at its start, stepped in exact 1/120 s steps); a loop keeps as many runs as particles live cycles, one starting each duration, so it wraps exactly. The FX record of a recipe effect carries the recipe's JSON (`recipe`) and, for any effect, the render settings that differ from its defaults (`render`). Emitter extras (#107): a `shape` to spawn on (line, ring or arc, rect area or edge, a polyline by arc length, or a layer's outline pixels, which `fx_from_recipe` reads into `points` so the stored recipe re-renders alone), `aim: "out"` (away from the shape), a `trail` (the last positions at 30 per second, drawn with Bresenham down the palette) and `curl` (curl-noise motion as a force or a flow).

**FX check**: `check_fx` (`fx_recipe_tools.ts`, `checkFxLayer`): read-only rules on effect layers (an FX record or an `AI: fx` name, not glow), each finding with sample coordinates and a fix. **spill**: the effect re-rendered from its record (`rerender` in `fx/render_record.ts`: a library id or stored recipe with `render`, a fluid from its settings, a blank-canvas pipeline with the sprite palette) at the recorded origin draws outside the sprite (error) or past its own canvas, where the placing tools cut it (warning); a record drawn on the sprite's own canvas (a pipeline over a layer, a fluid from `emit_layer`) cannot spill; without a record, pixels on the sprite's border. **one-shot-end**: judged on the placed cels, however they were timed (resampled, retimed, cut on a tag): the layer's last cel with content still draws more than `END_TAIL_PX` (8) opaque pixels, so the effect pops off there or is cut by the sprite's end; the message adds when the re-rendered end (t = duration) draws too. **loop-seam**: the change from the layer's last frame back to its first is more than twice a normal neighbouring step (90th percentile of pixels that differ) and more than 12 px. **colors**: more distinct RGB colors on the layer than `max_colors` (24); soft library effects (smoke, fire) blend thousands, so it warns there by design.

**Sprite effect**: an effect made from a layer's own pixels (#104-#107), as opposed to an FX library effect drawn from nothing. The shared seam is `agent/bridge/src/sprite_fx/write.ts`: `writeEffect` puts the effect's frames on a new `AI: <name>` layer above the source and hides the source; every frame the effect does not fill gets a copy of the source's cel, so the sprite looks the same there. **Insert** placement puts new frames after a frame (other layers' cels linked to it, tags grow); **over** placement replaces existing frames of the copy. One `put_images` request, so one undo step. `effectPreview` makes the contact sheet the tools return.

**Pixel-safe warp**: `warp` in `agent/bridge/src/sprite_fx/raster.ts`: an inverse map (scale, lean, rotation, row wave, offset about a pivot) where each output pixel takes one source pixel, so no new colors appear. Rotations sample an 8x upscale made by three Scale2x (EPX) passes, RotSprite's idea, reimplemented; scales, leans and waves take the nearest source pixel, and a shrink keeps thin details (an opaque pixel unlike both neighbours across the shrunk axis, such as an eye) that its footprint would skip; whole-pixel moves copy directly.

**Juice**: the `juice` tool (`agent/bridge/src/juice_tools.ts`, plan in `sprite_fx/juice.ts`, curves in `sprite_fx/curves.ts`): squash, stretch (area kept: sx = 1 / sy), wobble (rows shifted more the higher they are, on a damped spring), bounce (decaying arcs, squash on landings), shake (decaying integer offsets), flash (the flash color on every other frame), pulse, spin, lean, pop_in and pop_out, as a Sprite effect.

**Smear**: the `smear` tool (`agent/bridge/src/smear_tools.ts`, pure functions in `sprite_fx/smear.ts`): smear frames and motion trails from a layer's motion, as a Sprite effect. The motion of a frame is its content's centroid minus the previous frame's (optionally refined per 4 px block by block matching, for a part that moves on a still body). Modes: sweep (the mask stamped along the motion, tapered), stretch, afterimage (darker, checker-dithered copies at past positions) and multiples (sharp copies along the path). It only uses colors of the art and the sprite palette and never blends alpha.

**Fluid FX**: smoke, fire, gas, steam and liquids simulated and drawn as pixel art by `fluid_fx` (`agent/bridge/src/fluid_tools.ts`, solvers and shading in `agent/bridge/src/sprite_fx/fluid.ts`). Gases (`GasSim`) run Stam's Stable Fluids on a MAC grid at 1x or 2x the canvas (semi-Lagrangian advection, a Gauss-Seidel projection on the face velocities, vorticity confinement, buoyancy from temperature, fuel that burns into heat with cooling); liquids (`FlipSim`) are PIC/FLIP particles (0.9 FLIP) with a density correction, rasterized as occupancy and thresholded. Both step at a fixed rate (40 Hz gas, 120 Hz liquid) from a seeded PRNG, so a seed gives the same frames. **Presets**: smoke-puff, smoke, torch, fire-burst, poison-gas, steam, splash, pour. The shown field (density, temperature, liquid depth) maps to a ramp with Bayer 4x4 dithering between steps; a pixel is a ramp color or fully transparent. A **seamless loop** simulates two cycles and crossfades the second cycle's fields into the first before shading. Placement is like `add_fx` (by the emitter's centre, timed by the sprite's frames, one `put_images`), on `AI: fx fluid <preset>`; its FX record has id `fluid:<preset>` and the tool settings as `render` (`fluidSettings` turns either into solver settings, so `check_fx` re-renders it).

**FX pipeline**: an effect as a JSON chain of steps (`agent/bridge/src/sprite_fx/pipeline.ts`, tool `fx_pipeline` in `agent/bridge/src/pipeline_tools.ts`, #107): name, source (a layer and frame, or a blank canvas w x h placed on the sprite), frames (a count, inserted after the frame, or `{ over }` existing frames), fps, loop, seed, palette and steps. Each step is `{ type, ...params }`; any numeric param may be animated over the effect's time t (`{ from, to, ease }` with the Juice easings, or `{ keys: [[t, v], ...] }`). Step types: outline, dissolve, displace, gradient_map, glow, noise_fill, palette_map, juice, flash, tint, offset. They live in a registry (`STEP_TYPES`, `registerStep`), the extension point for the smear and fluid steps. Every frame runs the chain at native resolution, then every pixel is snapped to the allowed colors (the working palette, colors the steps name, the source's own) with alpha 0 or 255. Over a layer it is a Sprite effect on 'AI: fx <name>'; the FX record has id `pipeline:<name>` and the pipeline's JSON in `recipe`, its source resolved (the layer's name and frame, or the canvas's x, y and frame). **Re-apply** (#97): a pipeline of the same name replaces its earlier run (`replace`, default true; false adds `AI: fx <name> 2`): one `put_images` request empties the old layer (`clear`) and rewrites it, from the recorded source unless the new pipeline names one, over the frames the earlier insert made (only extra frames are inserted; surplus ones show the source again).

**Noise**: seeded coherent noise in `agent/bridge/src/sprite_fx/noise.ts` (written from the papers): value, Perlin's improved noise (2002), simplex (Gustavson's explanation, 4D by ranking) and Worley F1 cellular, each in 2D, 3D and 4D, with fBm. Looping noise samples 4D noise on a circle in the two extra dimensions, so the last frame of a loop leads exactly back to the first. `curl2` is the curl of a noise potential by central differences (Bridson et al. 2007), used for curl-noise particle motion in FX recipes.

**Light layer**: a shown image layer that does not blend Normal (an Addition glow), or an `AI: fx … glow` layer. `check` skips the per-pixel rules on them; `export_for_engine` puts them on the **glow sheet**.

**Pixel FX skill**: the built-in skill that ties the FX tools together (`agent/skills/pixel-fx/SKILL.md`): pick from the FX library (`list_fx`, `preview_fx`) or write an FX recipe when nothing fits, place with `add_fx` or time to an attack with `fx_overlay` and `hit_stop`, then `check_fx`, `check` and FX export. Its timing and "you see / fix" tables are the house rules for effects.

**FX export**: what `export_for_engine` does with effects (`fxExport` in `agent/bridge/src/export_tools.ts`). **Pivot**: an explicit `pivot` wins; else a sprite whose shown image layers are all effects or light layers (an effect sheet) is pivoted on its top effect's origin; else bottom-center (a character with effects keeps it). A non-default pivot is also written on each JSON frame (`pivot`, which Phaser's atlas loader takes as the origin), and Godot's HOW_TO gives the AnimatedSprite2D offset. **meta.fx** in the JSON (all engines): `{ id, fps, loop, windup, origin, hits: [{ frame (0-based), freeze_ms, shake_ms?, amp? }], effects? }` (the first effect's fields; `effects` lists them all when there are several; `{ hits }` alone for a character with hit-stops and no effect). **Glow sheet**: with light layers, `glow: "sheet"` (default) writes `<name>_glow.png` laid out like the color sheet (trimmed to both, `meta.glow`, a Godot `<name>_glow.tres`), the light layers summed for additive drawing (`composeLight`), and composes the color sheet from the other layers (`composeNormal`, Aseprite's normal blend at layer opacity); `glow: "baked"` uses Aseprite's own render with the glow in.

**Chat**: one conversation in the Chat Panel, with its own messages, draft, queue, Turns, Mood and agent process, belonging to one sprite (`agent/extension/chats.lua`, `chat_panel.lua`). Each sprite has a list of chats, shown as tabs; chats run their turns at the same time, and a chat's tool requests (marked `origin: "chat"` with its id) run on its own sprite as document-scoped requests (`Panel.handleRequest` passes the chat's sprite as the request's doc), without switching the user's tab.

**Document-scoped request** (#90): a request that names the sprite it acts on (protocol 42, protocol.json `routing`): `doc` in the JSON-RPC envelope (`RequestRoute.doc` on the bridge; a **sprite id** `S12` from get_state's `SpriteSummary.id`, `SpriteInfo.doc`), else the chat's sprite, else the active sprite; a doc of a closed sprite is an error. `H.call(method, params, bytes, route)` resolves it once (`resolveSprite`) into the request's **site** (`D.site()`: sprite, frame, layer, active), and handlers act on the site instead of `app.sprite`. A sprite that isn't the active tab gets the frame and layer it had when last active (`noteSite`, called on every `sitechange`; frame 1 and its top image layer when never seen). Its change is one undo step on that sprite (`D.transaction`: the fork's **`sprite:transaction`** when the build has it, else `app.transaction` with the sprite made active for that call); undo and redo move that sprite's history (`sprite:undoTo`). **Activation** (`D.withActive`): the parts only Aseprite's active document can do (agent-written Lua, `app.command`, `app.range` with LinkCels) make the sprite active for the call and give the user's sprite, frame and layer back; requests marked `activates` in protocol.json (`execute_lua`, `run_command`, `apply_timeline_text`) run entirely so, and `put_images`' insert links cels so. A sprite a request makes or opens comes back as `route.moved` (the chat moves there). The bridge sends a doc only when a caller names it (`withDoc(requester, doc)`, the HTTP endpoint's `?doc=`, HeadlessLink's request line), since the extension owns which sprite a chat is on.

**Style memory**: the conventions the user approved for a project (#93): palette roles, the outline rule, the pixel scale (one entry each; a new one replaces the old) and up to 20 notes. The agent proposes an entry with `remember_style`, which posts a `memory` chat event; the panel shows it as a card with Remember / Don't remember (the `ask_user` card), and Remember stores it in the sprite property aseprite-agent "style.memory" (JSON, one undo step, `agent/extension/project_memory.lua`). The State block lists the entries as `style memory` lines with every message.

**Project folder**: where a chat's agent runs (#93): the sprite's folder when it is saved (not the home folder or a drive root), else the shared workspace (`~/.aseprite-agent/workspace`). The bridge writes a short `AGENTS.md` there on first use and keeps its style memory section (between `aseprite-agent:style-memory` markers) in step with the sprite; a file without the markers is the user's and is left alone. A conversation keeps the folder it started in (recorded in the agent home), since agents keep their sessions per folder (`agent/bridge/src/project.ts`).

**Checkpoint**: a copy of a chat's sprite taken when a message starts an Agent or Developer turn (#93), as an .aseprite file in `~/.aseprite-agent/checkpoints/<sprite title>-<path hash>/` (unsaved sprites: `unsaved-<title>-<id>`; the last 20 per sprite are kept), plus the sprite's **undo state id** at that moment. Kept on the message's user entry; a turn on an unchanged sprite reuses the previous file (`agent/extension/checkpoints.lua`). Not the same as `diff_visual`'s named canvas checkpoints.

**Rewind**: the ↶ action on a user message (#93), like Claude Code's `/rewind`; each choice means "just before this message". **Restore sprite** goes back through the undo history to the checkpoint's undo state (Redo brings the later work back; a copy of the work is checkpointed first) or, when the history no longer reaches it, opens the checkpoint as a new tab; a message that ran no Agent turn uses the next checkpoint after it. It warns when other chats ran turns on the sprite since, and refuses while any chat works on it. **Restore conversation** drops the message and what followed (`Conversation:truncateAt`), puts the message back in the prompt box and forgets the provider conversation ids; the next message carries a **recap** of the kept messages (`<earlier-conversation>`, `Conversation:recapText`) into the agent's new session. **Branch from here** opens the checkpoint as a new tab named next to the original (`<title>-branch.aseprite`, so Save never writes into the checkpoints folder) with a new chat holding the earlier messages and the recap.

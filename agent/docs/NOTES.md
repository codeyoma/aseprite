# Implementation notes

One short entry per change: how it works, why it was done this way, and where it sits in the architecture. Newest first. These notes are for future refactoring; terms are in `GLOSSARY.md`.

## Windows stable updates rebuild in Visual Studio's environment
- **How:** when the stable source already has a build, `stable.mjs prepare` on Windows writes `<stable root>/vs-build.cmd` (call vcvars64.bat, found with vswhere as build.cmd does, then `cmake --build build -- aseprite`) and runs it. A first build still goes through `build.cmd --auto --norun`; macOS and Linux are unchanged.
- **Why:** outside Visual Studio's environment neither cmake nor the compiler is on PATH, and `build.cmd --auto` cannot rebuild: once a build exists, build.sh lists it, prints "No build selected" and exits 0. So the first update after an install (and every Check for Updates) installed the new extension and bridge with the old aseprite.exe.
- **Architecture:** the installer owns how a rebuild runs per platform; build.cmd stays the first-build path.
- **Follow-up (bridge dependencies):** `prepare` runs `npm ci` only when `agent/bridge/package-lock.json` changed since the install (or there is no install or `node_modules`), and again when the bridge build fails. On Windows the running stable bridge keeps its pre-warmed agent's `claude.exe` (in `node_modules`) open, so `npm ci` failed with EPERM while Aseprite was open, after deleting part of `node_modules`; a failure there now says to close Aseprite and update again.

## Windows draws at the screen's resolution: Screen Scaling 100%, UI Elements 200%
- **How:** on Windows the fork's first run (`create_main_window`, `scale == 0`) keeps the window at scale 1 and puts the factor upstream would use as Screen Scaling into UI Elements Scaling (`general.ui_scale`): the same size on screen. An existing install changes it in Edit > Preferences > General (or `[general] screen_scale = 1`, `ui_scale = 2` while Aseprite is closed). LCD text (previous entry) is only used when the canvas reaches the screen 1:1 (`display->scale() == 1`).
- **Why:** upstream's first run picks Screen Scaling 200% on a large screen, which draws the whole window at half resolution and lets the window double every pixel. Pixel art is fine with that, but the chat panel's system-font text was rasterized at about 7 px and shown doubled, so it looked low-res however it was antialiased (and LCD colors were doubled with it).
- **Architecture:** the UI keeps Aseprite's pixel look (its fonts and icons scale by UI Elements Scaling); only what is drawn in device pixels (system-font text, the canvas) gains resolution. macOS is unchanged (not checked there).

## The repository's MCP bridge uses the dev home (`--dev`)
- **How:** `.mcp.json` starts `agent/bridge/dist/index.js --dev`. With no `ASEPRITE_AGENT_HOME`, `--dev` sets it to the dev instance's home (`ASEPRITE_AGENT_DEV_HOME` or `~/.aseprite-agent-dev`, as `tools/instances.mjs`) in `session.ts`, so what the bridge starts agrees.
- **Why:** a Claude Code session in this checkout started its bridge in the default home. On the Windows PC that session began before `stable.mjs update` pinned the home, so its stdio bridge (protocol 39, from before a pull) stayed in the stable home's `session.json`. The newly installed stable Aseprite (protocol 42) connected to it and stopped with "Update the bridge so both come from the same release"; it never started its own daemon while that bridge answered.
- **Architecture:** a coding session drives the dev instance, like the live tests. The stable instance is reached through its own pinned bridge: its panel's daemon, or a user-scope MCP entry for `~/.aseprite-agent-stable/src/agent/bridge/dist/index.js`.

## Sharp chat text on Windows; Korean no longer crashes the panel
- **How:**
  - The `font = "system"` text of script dialogs (the chat log canvas, its labels, the prompt box) is laid out at subpixel positions with slight hinting (`dialog_class.cpp`); fallback fonts (Korean) are copies of that SkFont.
  - A full-resolution canvas (`autoscaling = false`) on Windows with ClearType on gets LCD text: laf's `SkiaSurface::setPixelGeometry` gives the bitmap's SkCanvas the screen's subpixel order (`SPI_GETFONTSMOOTHINGORIENTATION`), and the canvas paints with an LCD-edged copy of its font (`Canvas::paintFont`). Labels and the prompt box are drawn on the window surface and stay grayscale.
  - `main.cpp` sets `LC_CTYPE` and `LC_COLLATE` back to "C" after `setlocale(LC_ALL, "en-US")`; numbers keep en-US.
  - Extension (also for stock Aseprite): text that is wrapped, collapsed or trimmed uses ASCII whitespace classes instead of `%s`/`%S` (chat log wrap, alert wrap, rewind question, recap, `/command` prompt, style memory), and truncation keeps whole UTF-8 characters (rewind question, style memory).
- **Why:**
  - With Skia's defaults (normal hinting, whole-pixel positions) DirectWrite crowded and spread letters ("drewa green"), and grayscale edges looked soft next to the rest of Windows.
  - "en-US" is a locale name only on Windows, so only there Lua's `%s` used code page 1252, where byte 0xA0 is a space. Many Korean characters contain it ("레" = EB A0 88), so the chat log split them and Skia's shaper aborted on the invalid UTF-8 (`ud2` in SkShaper): a Korean reply with "레이어" closed Aseprite. The same locale made `"~" < "Color"` true.
- **Architecture:** Windows now has the byte-wise C character classes and collation that macOS and Linux already had, so Lua scripts behave the same everywhere. LCD text needs an opaque surface shown 1:1, which only the full-resolution canvas has. Limit: one subpixel order for all monitors (a portrait monitor shows color fringes).

## Windows: the first run on a PC (#108)
- **How:**
  - Panel bridge start: the extension still runs `start "" /B node ... --daemon`; on Windows the daemon starts itself again detached (`platform.ts` `BACKGROUND`) and exits, so cmd's console window closes. Every console program the bridge starts passes `windowsHide` (`HIDDEN`); that hidden console is inherited by the agents' own children.
  - A dead bridge is found: the reconnect timer pings the bridge every 2 s (on Windows a killed peer shows only when the socket sends), and `ensureBridge` starts a daemon when the session file's port refuses the connection (a killed bridge leaves its `session.json`).
  - `stable.mjs`: `runningStable()` lists `aseprite.exe` by path through CIM; `waitUnlocked()` opens the program for writing (Windows renames a running program, so the old rename probe passed at once); `.\build.cmd`.
  - Lua patterns that build names use ASCII ranges, not `%w` (checkpoint folders, new skill files, document URIs); the composer sorts commands last by rank, not by a `"~"` key.
  - C++: `FontInfo::getFromPreferences()` uses Aseprite's font by name when there is no main window, instead of dereferencing it (batch `PasteText`/`render_text` with no saved text-tool font crashed).
  - Tests: `npm test` and `run_lua_tests.mjs` use throwaway agent homes and user folders; `gen.mjs` finds Python through `py`/`python`; `gen_commands.py` writes LF; the Codex auth falls back to a hard link before a copy.
- **Why:** on Windows the panel's daemon kept a console window open; after a bridge was killed the panel never started a new one; an update could start deleting `app\` while Aseprite still ran. Aseprite sets the `en-US` locale (a valid name only on Windows), so Lua's `%w` and string `<` follow Windows collation there: Korean titles gave invalid UTF-8 folder names and `"~"` sorted first. A fresh user folder (no text-tool font) exposed the upstream batch crash.
- **Architecture:** process options per platform live in `platform.ts`; the extension decides "no bridge" from the socket, not from the session file alone.

## main stays official; a workflow syncs it and merges it into agent
- **How:** `.github/workflows/sync-upstream.yml` (on `agent`, the default branch, so its schedule runs) runs every 6 hours and by hand. It fast-forwards `main` to `aseprite/aseprite` main (never anything else), then merges `main` into `agent` when `agent` lacks it. A conflict, or a refused push, pushes nothing and opens one issue with the local steps. An optional `SYNC_TOKEN` secret (a token with the workflow scope) lets the merge carry upstream workflow changes and starts the agent CI on the merge commit; `GITHUB_TOKEN` can do neither.
- **Why:** `main` had been pushed to `agent`'s tip by mistake and was restored to the official commit. Keeping `main` a pure mirror keeps upstream updates a plain fast-forward, and the merge brings them to the agent layer without anyone remembering to.
- **Architecture:** repository automation only; `AGENTS.md` says where agent work goes.

The base pose that character-motions keeps as frame 1 makes 11 frames, which the judge reads as a mismatch (fit 1-2).
- **Architecture:** benchmark runner and data only.

## Document-scoped requests: each request names its sprite (#90)
- **How:**
  - Protocol 42. The JSON-RPC envelope may carry `doc` next to `origin` and `chat` (protocol.json `routing`); get_state's `SpriteSummary` has `id` (`"S" .. sprite.id`). Requests marked `activates` (`execute_lua`, `run_command`, `apply_timeline_text`) run with their sprite active.
  - Extension: `H.call(method, params, bytes, route)` resolves `route.doc` (`resolveSprite`: `"S12"` or 12; a closed sprite is an error, never the active one) into the request's **site** `{ sprite, frame, layer, active }`. wire_params resolves layer and frame refs against that sprite. Handlers read `D.site()` (outside a request, the active sprite's site) and change the document through `D.transaction(sprite, label, fn)`; they move the user's frame and layer only when the sprite is on screen (`D.select`), otherwise the remembered site. A sprite not on screen defaults to where it was when last active (`noteSite`, on every `sitechange` and at each call's start; else frame 1 and its top image layer).
  - `D.withActive(sprite, fn)` makes the sprite active for what needs Aseprite's active document and gives back the user's sprite, frame and layer (also after an error); it counts activations (`H.stats()`) and notes a sprite the call made (`site.moved` → `route.moved`).
  - Still activating (the only places): `execute_lua` (agent-written Lua stays foreground-only), `run_command` (`app.command`), `apply_timeline_text` (LinkCels/UnlinkCel over `app.range`), `put_images` with `insert` (LinkCels over `app.range`, inside the sprite's transaction), and on a build without `sprite:transaction` every transaction (`D.transaction` falls back to `app.transaction` with the sprite active). `render_text` makes and closes its own scratch sprite and gives the tab back as before; `create_*` make a new sprite (the chat moves there). The sub-agent cursor (`app.range.frames`) is only drawn when the sprite is on screen.
  - Undo and redo move the request's sprite's history with `sprite:undoTo` (`stepHistory`: the previous or next state in the history's list, as `app.undo`/`app.redo` do), not `app.undo`.
  - Step capture and guards per sprite: `capture:aroundSite(site, ...)` captures the site's sprite and frame (or a sprite the request made) and keys the step by that sprite; claims merge steps only on the same sprite and frame; `diff_visual` compares the routed sprite with its own last step. The scope guard and the motion gate snapshot and undo (`sprite:undoTo`) the request's sprite; "switched to or created another sprite" now comes from `site.moved` instead of comparing `app.sprite`.
  - `get_state` and `state_block` with a site describe the routed sprite as `activeSprite` with the site's layer, frame, tag and cel; zoom and the timeline range (the screen's) are left out for a sprite not on screen.
  - Chat panel: `Panel.handleRequest` no longer swaps the tab. It passes the chat's sprite as the doc (an envelope doc wins), rehomes the chat on `route.moved`, and when a background chat made a sprite gives the user's tab back.
  - Bridge: `RequestRoute` gets `doc`; `toolContext` now passes the route through (it dropped it); `withDoc(requester, doc)` binds a requester to a sprite; the chat HTTP endpoint takes `?doc=`; `HeadlessLink.request(..., route)` puts `doc` on the JSON line and `headless_runner.lua` passes it to `H.call`. `SpriteInfo.doc` and get_context's sprite carry the id. The fake document routes by doc too (a site per sprite), so the contract scenario `tests/contract/routing.json` (`routed: true`: a second sprite is active while every step names the fixture) runs on the fake and in headless Aseprite.
  - Fork (C++): `sprite:transaction([label,] fn)` (`src/app/script/sprite_class.cpp`) runs `fn` in a `Tx(doc, label)` on that sprite's document (lock, join or start its transaction, commit, rollback on error, results returned), like `app.transaction` does for the active document. `Transaction` records the undo position (active layer and frame, timeline range) only when its document is the active one (`positionContext`), and only then sets the current palette on a color change; `cmd_undo.cpp` skips "go to modified" for a step with no recorded layer and never selects a layer of another sprite. Before this, any script change to a background sprite recorded the active sprite's layer id, and undoing it in the GUI could select a layer of another sprite.
  - Tests: `tests/document_scope_test.lua` (two sprites; writes, explicit refs, undo/redo, dry run, apply, get_state/state_block, capture keys, diff_visual, scope guard, execute_lua activation and its sprite, unknown doc; once with `sprite:transaction` and once with it turned off; `sprite:transaction` itself), a routed sweep over every request in `tests/policy_test.lua` (the user's tab, frame, layer and history untouched; writes captured on the routed sprite; no activation except `activates`), `bridge/test/document_route.test.mjs` (protocol 42, route through toolContext/withDoc/AsepriteLink envelope/HTTP `?doc=`/HeadlessLink, and with `ASEPRITE` the headless runner writing to the named sprite). Lua tests pass on the fork build with `sprite:transaction` and on a build without it.
- **Why:** parallel chats (3fbdd907b) ran each request with its chat's sprite swapped in and out of the active tab, which switches tabs visibly, fires site changes, and depends on Aseprite's active document for every handler. Most handlers are plain Lua on a Sprite object and need no active document; only `app.transaction`, commands, `app.range` and the undo commands do. `sprite:transaction` (a small C++ addition mirroring `App_transaction`) removes the last reason for ordinary writes, and `sprite:undoTo` already existed.
- **Architecture:** the extension owns which sprite a chat is on (a chat moves when a request makes a sprite), so the bridge does not stamp chat requests with a doc (a copy there would go stale); a doc in the envelope is for callers that pick a sprite (stdio/CLI sessions, an endpoint bound with `?doc=`) and always wins for that one request without rehoming the chat. The site is resolved once per request and passed to capture, guards and views, rather than read from `app.*` in each piece. Codex (second opinion, read-only) agreed with envelope `doc` over a param, with not sending it for chat turns, and with remembered frame/layer defaults; it flagged that `toolContext` dropped the route (fixed), that `CmdTransaction` records both the active site and the timeline range from the active context (fixed with `positionContext`), that a default `SpritePosition` still holds frame 0 (cmd_undo now skips a position with no layer), and that `Transaction::commit` set the global palette from a background document (now only when active). Open: no live GUI test yet of background transactions (redraw of a background tab, the Undo History window, LinkCels activation inside `sprite:transaction`); the CLI has no `--doc` option; sub-agents still follow the chat's sprite rather than a scratch copy (the "sprite worktree" idea in the issue); `put_images`' insert and the `activates` requests still switch tabs briefly.

## Wire seam: each side checks what it receives, once; get_context folded into get_state (#96)
- **How:**
  - Protocol 41. `protocol.json` now describes the bridge methods' params (`bridgeMethods` is an object, name -> `{ params }`), named **shapes** (`Attachment`, `MemoryEntry`, `State`, `Sprite`, `SpriteSummary`, `Layer`, `FxRecord`, `Hit`, `Tag`, `Frame`, `Palette`, `Slice`, `Rect`, `Brush`, `Cel`, `TimelineRange`), and get_state's result (`"result": "State"`). The type grammar grew `T[]` (list), `T{}` (map) and shape names; `"...": "Other"` includes another shape. Unknown fields are errors everywhere, null counts as missing, and `[]`/`{}` stand for each other because Lua's json.encode writes an empty table as `[]`.
  - One checker per language with the same rules and messages: `protocol.ts` (`parseType`, `checkParams`, `checkBridgeParams`, `checkShape`, `checkResult`) and `wire_params.lua` (`parseType`, `check`, `checkBridgeParams`, `checkResult`). Messages name the method and a 0-based param path: `chat.send: 'attachments[0].path' must be a string`; articles are now right (`must be an integer`).
  - Who checks: the extension checks request params on arrival (`wire_params.lua`, which also resolves layers and frames); AsepriteLink and HeadlessLink no longer run `checkParams` before sending, only the method-name check. AsepriteLink checks a bridge method's params before its handler (`handleInbound`), and both links check a typed result when it arrives (`settle`), so every consumer of get_state (tools, `infoOrNone`, `/files`, the raw `get_state` tool) gets a checked State. Tool inputs stay checked by zod. The fake document runs `checkParams` in the extension's place and checks its own typed results, so the fakes stay in shape.
  - get_state carries the user's context: `brush`, `zoom`, `activeTag`, `activeCel` (layer id, frame, bounds, opacity) and `timelineRange` (layer ids, frames), next to the existing tool, colors, active layer and frame. `document_view.lua` builds it once (`contextOf`); `getState`, the panel's context line and the State block's active and timeline lines read it. The `get_context` request and `getContext` are gone; the `get_context` tool (still a core tool) requests get_state and returns `contextOf(state)` from `document.ts`, with layer paths as before plus `layerIds`.
  - `fxRecordOf` and `fxHitsOf` copy the stored property as it is instead of re-listing its fields: the fields live in `handlers_sprite.lua` (writer), `protocol.json` (`FxRecord`, `Hit`) and `fx/record.ts` (meaning).
  - Contract suite: `tests/contract/wire.json` (a State with nested and empty groups, an effect record, hits, a spec, slices and the selection; bridge-method params and errors) runs on the fake and in headless Aseprite; both runners check every typed result against protocol.json, and the new `bridgeMethod` step runs each side's checker. `bridge/test/wire.test.mjs` covers the links (a bad `chat.send` never reaches its handler; a bad State is rejected with its path) and the get_context view; `wire_params_test.lua` checks the grammar and the extension's real get_state (no sprite, groups, tags, slices, selection).
- **Why:** request params were checked three times (zod, `checkParams`, `wire_params.lua`) while bridge methods such as chat.send were not checked at all, get_state's shape was known separately by `document_view.lua` and `document.ts` with no check that they agree, and get_context re-described part of get_state with its own reads of app state.
- **Architecture:** the receiver is the authority for each direction, because the extension must resolve references against the live sprite on arrival anyway and must not trust its input; a sender-side check would only add a second copy. The cost is a round trip for a bad param, which zod already makes rare for tool calls. Codex (second opinion) agreed with receiver authority and suggested checking results at a shared receive point in both transports rather than in `parseState` (done: `checkResult` in the links; `parseState` stays the mapping), keeping the `scope` exception request-only, defining maps and nullable fields explicitly, accepting only an empty `[]` for an object, bounding recursion (depth 32) and testing failure paths on both sides. Strict results mean any new field in get_state is a protocol change with a version bump, which the exact-version hello already enforces. Open: request params a handler checks itself in more detail (put_images' images, apply's ops) are still typed loosely (`array`, `object`) in protocol.json.

## Long alerts wrap instead of widening
- **How:** `Prompter.wrap` breaks alert text at spaces into lines of at most 72 characters (UTF-8 aware; a longer word is cut), keeps given newlines, and stops at 30 lines with "…". `Prompter.alert` is app.alert with that wrapping; the panel's questions, the bridge connection's alerts and saved-command errors all use it.
- **Why:** a long permission text or error made the alert as wide as its longest line, sometimes wider than the screen.
- **Architecture:** one alert adapter in `prompter.lua`, passed to `bridge_connection.lua` and `saved_commands.lua` as `alert` (they fall back to app.alert).

## Two Aseprite windows no longer fight over the bridge
- **How:**
  - A newer Aseprite connection still replaces the older one, but the bridge first sends it `replaced` (protocol.json handshake). The extension then closes without its automatic reconnect and waits until its user uses the agent again.
  - A reopened socket counts as disconnected until `welcome`, so no request goes out before the hello.
  - `recordBridge` leaves a pinned `bridge.json` alone, also when the pinned bridge itself starts.
  - `stable.mjs` finds running stable Aseprites by executable path: `--wait` waits for all of them, and `start` does not open a second one.
- **Why:** two stable windows (one from `stable.mjs --start`, whose pid file was stale) took the bridge from each other several times a second. Requests sent mid-handshake were rejected as `bad hello (skills.list)`, so the `/` skill picker stayed empty. The pinned bridge also rewrote `bridge.json` without `pinned`.
- **Architecture:** one Aseprite per bridge stays the rule. The window that last used the agent owns it; the other one is told and waits.

## Binary pixel transport and native check helpers (#95)
- **How:**
  - Protocol 37 adds the `bytes` param type (the `rgba` of put_image, create_sprite, create_tilemap, each put_images image and each create_animation frame): base64 text, or `{offset, length}` into the request's binary frame. `document.ts` passes the raw `Uint8Array`; `AsepriteLink.request` runs `packBinary` (protocol.ts), sends the JSON with a top-level `binary: <length>`, then one binary frame with every image back to back. `HeadlessLink` runs `base64Bytes` instead, since JSON lines carry no frames.
  - `bridge_connection.lua` holds a request with `binary` until the next BINARY message, checks its length, then dispatches it with the blob (held requests keep theirs). A text frame first, or a wrong length, answers the request with an error. `H.call(method, params, blob)` keeps the blob for that call; handlers read pixels through `D.bytes` (`wire_params.bytes`), which decodes base64 or slices the blob with `string.sub`, and assign it to `Image.bytes`.
  - The fork's Lua `Image` gets `histogram()` (pixel value -> count) and `isolatedPixels([limit])` (count, first positions of pixels with no same-valued 8-neighbor) in `src/app/script/image_class.cpp`. `handlers_check.lua` uses them when present: the histogram gives the off-palette colors and the semi-transparent count, `string.find` over `Image.bytes` (4-byte aligned) finds the sample positions of the reported colors only, and `isolatedPixels` is the orphan rule. Without them (stock Aseprite) check walks the pixels in Lua as before; `H.setNativeCheck(false)` forces that path for tests.
  - Measured with `node agent/tests/bench/native_bench.mjs` (headless, 12 frames of 256x256 palette art, medians of 5): put_images 152 ms -> 5 ms (base64 decode alone was 145 ms); check over 12 frames 1342 ms -> 8.8 ms, one frame 104 ms -> 0.8 ms, with identical findings. On the bridge, packing is 0.2 ms vs 1.0 ms for base64. No live WebSocket or GUI number yet.
- **Why:** the Lua base64 decoder and check's per-pixel closures were the remaining hot spots after #91. Binary transport removes the decode instead of moving it to C++, and the same framing already carried results the other way. The native helpers stay generic image primitives; palette policy, sample limits and findings stay in Lua. Codex reviewed both designs (agreed; suggested bounding sample searches, rejecting bitmap images, and a deadline for a frame that never arrives).
- **Architecture:** transport encoding lives only in the two links; the Document and tools deal in raw bytes, and test fakes accept them (`Buffer.from(u8, "base64")` copies a typed array as is). base64 stays accepted for older callers and the Headless runner. Left for later: a deadline for a binary frame that never arrives (today the next text frame errors it, and the bridge's request times out), and a live measurement of write and check stalls in the GUI.

## Project memory, checkpoints and rewind (#93)
- **How:**
  - Style memory: `remember_style` (core tools, kind read) posts a `memory` chat event (protocol v37: event type `memory`, field `topic`). The Conversation records it as a `memory` entry; the panel draws it with the `ask_user` card (now `cardRows`). Remember calls `project_memory.lua`, which writes the sprite property aseprite-agent "style.memory" in one transaction on the chat's sprite. `document_view.lua` adds the entries to the State block.
  - Checkpoints: `startTurn` takes one for Agent and Developer messages before `chat.send` (`checkpoints.lua`: `saveCopyAs` into `<home>/checkpoints/<key>/<time>-<seq>.aseprite`, deduped by undo state id, the last 20 per folder kept) and stores it on the user entry, which serializes with it. Every turn start is logged per sprite and chat (`noteTurn`), so a rewind can name other chats whose edits it would undo.
  - Rewind: ↶ left of a user bubble opens `Prompter.rewindQuestion` (Restore sprite / conversation / both / Branch). Restore sprite uses `sprite:undoTo(rec.undoId)` when the history still has that state (after checkpointing the current work), else opens the file as a new tab. Restore conversation is `Turns:truncateAt` (Conversation truncate, `last` reset to the last kept reply), with the message put back in the prompt. Branch opens the file under a new name next to the original and fills the new sprite's chat with `Conversation:branchData`.
  - Recap: after a truncate or branch, `recapToSend()` builds the kept messages (user text, replies, one line of steps per turn, answered questions; no thoughts or tool output) and `chat.send` passes it as `history`; the bridge puts it first as `<earlier-conversation>` (cut to 8000 chars from the start). The `session` event of the new conversation ends it.
  - Project folder: the panel sends the sprite's file and style memory with `chat.send` and `chat.warm`. `project.ts` picks the folder (`turnDir`), creates or updates `AGENTS.md` (`ensureProject`) and records each conversation's folder (`ConversationDirs`).
- **Why:** the chat's working directory was one shared workspace (no project memory), revert worked only through the undo history (lost when a sprite closes), and a conversation could not be branched. Decided with the user: memory the agent proposes and the user approves; Claude Code's /rewind for sprite and conversation; HyperFrames-style init in the sprite's folder.
- **Architecture:**
  - Second opinion (Codex, read-only): take checkpoints at turn start, not lazily before the first write (a lazy one would include edits made in between); prefer the native undo history with a safety copy over rebuilding a sprite from the file, since a rebuild loses linked cels, slices, properties and tilemaps, so the fallback is a new tab and never a partial overwrite; block restores while any chat works on the sprite and warn about other chats' later turns; a recap instead of an ACP session fork is fine for a first version; warm agents in the folder a new conversation would use, since `AcpRuntime` drops the conversation when a runner's folder changes.
  - Undo id 0 means "before any step", so `undoTo(0)` is used only for the same sprite object (sprite ids are unique within a run). Checkpoint files outlive the undo history (a sprite reopened, Aseprite restarted), so the file path is the fallback.
  - Conversations that predate #93 have no recorded folder and keep running in the shared workspace, so their sessions still load.
  - All file access stays in `agent.lua` (save, remove, list, open): `checkpoints.lua` gets them as functions and is tested with fakes and with a real sprite in batch mode (`tests/rewind_test.lua`).

## Declarative apply and a smaller default tool set (#88)
- **How:**
  - `apply` takes a list of ops (`add_layer`, `set_layer`, `move_layer`, `delete_layer`, `pixels`, `rect`, `line`, `clear_cel`, `move_cel`, `add_frames`, `delete_frames`, `set_duration`, `set_tag`, `delete_tag`, `set_palette`, `append_palette`). It returns the change per op, the errors by path, the layers added and the frame count. `look`/`check` return the snapshot and findings with the result, as with `execute_lua`.
  - write_pixels' grid code became `gridKeys`/`gridWrites`/`celWrites` in `document_handlers.lua`, and set_palette's body `paletteColors` in `handlers_color.lua`, so `apply`'s pixel, rect, line and palette ops run them inside the outer transaction. Rects and lines clip to the canvas; colors are hex, `.` or a palette index.
  - `tool_sets.ts`: `CORE_TOOL_NAMES` (13 tools) plus `find_tools` and `call_tool` are what `createMcpServer` lists (`serverTools`); `call_tool` runs any tool the endpoint allows (read-only, sub-agent and critic filters apply), after `safeParse` against its schema. `skillToolsNote` adds the signatures of a skill's deferred tools to the chat's skill context, `read_guide(skill)`, the MCP skill prompts and the plugin's skill files; the chat prompt gets a `<more-tools>` block for the deferred tools the basics guide names. The panel shows a `call_tool` step as the tool it runs. `ASEPRITE_AGENT_TOOLS=all` lists everything.
  - Measured (tools/list JSON over MCP): 91 tools, about 135k characters (about 34k tokens) before; 15 tools, about 16.5k characters (about 4k tokens) after.
- **Why:** an edit took 3-6 model calls of about 2.7 s each, and 81+ fine-grained tools invited small steps and wrong tool names. One `apply` call replaces a chain of Lua snippets and timeline calls with one undo step, and its dry run and op-path errors let the agent fix a plan without retrying blindly. A dry run that really runs and rolls back is exact against the live sprite, without a second simulation of Aseprite in the bridge. The op grammar sits in the tool's description and `ops` stays loose in the registered schema: a JSON Schema union of 16 ops would have tripled the tool's size. Codex (second opinion) agreed with the wire method and rollback dry run, and suggested the strict per-op schema, op-path errors, safeParse in call_tool and keeping the endpoint filters inside call_tool; its core pick favored diff_visual and list_skills over the timeline tools, which stay reachable through call_tool.
- **Architecture:** `apply` is a scoped write: a sub-agent may only use the pixel and cel ops (the scope guard checks cels, not tags, palette or layers). The active layer and frame are restored after the ops. Ops after a failed one still run, so later errors may follow from an earlier one. The listed tool set is fixed per MCP server rather than changed with `tools/list_changed`, because the chat's HTTP endpoint makes one server per request and clients differ in re-listing. The CLI and tests use the full Tool table. Contract scenarios `tests/contract/apply.json` run on the fake document and in headless Aseprite; `tests/apply_test.lua` checks the single undo step, rollback, indexed colors and the sub-agent restriction.

## Smears, afterimages and multiples (#105)
- **How:**
  - `sprite_fx/smear.ts` holds pure functions. `motionVector` is the centroid difference between two frames. `blockMotion` refines it per 4 px block: it searches displacements within 3 px of the coarse vector and keeps the one with the smallest sum of absolute RGBA differences over a 5x5 window, plus a small pull towards the coarse vector so flat areas follow the body.
  - `sweep` stamps every opaque pixel back along its trail, one step per pixel on the long axis (the Bresenham/DDA points), farthest first. Each copy is squeezed across the motion as it trails (taper) and the far third is checkered (thin). It fills with the art's three main colors (lightest at the head), its outline color, or each pixel's own, and draws the art itself on top.
  - `stretch` is an inverse map along and across the motion (s and 1/s) about the leading edge, sampling the 8x Scale2x upscale like the warp. `afterimage` draws the previous frames' art (or the frame moved back along a given vector), each ghost one more step to the nearest darker palette color, through a checker. `multiples` draws sharp copies along the path.
  - `smear_tools.ts` reads the frames, measures each frame against its previous one, smears the frames that move at least `min_px` (over) or inserts one frame (`insert_after`), and writes through `writeEffect`.
- **Why:** the third family from `docs/fx-algorithms-research.md` §2. Smear frames read as speed in pixel art only when they stay crisp, so trails reuse the art's colors and checker dithering instead of alpha. The SMEAR paper's code is GPL-3, so only its ideas are used.
- **Architecture:** a Sprite effect on `AI: smear <layer>`, one `put_images` request. A tag's first frame has no previous frame unless `loop: true`, because a dash that jumps back to its start is not motion. In insert mode the new frame shows the next frame's art with the trail back to the frame before.

## Fluid effects: smoke, fire, gas, liquids (#106)
- **How:**
  - `sprite_fx/fluid.ts` holds two solvers written from the papers. `GasSim` is Stable Fluids on a MAC grid: forces (buoyancy from temperature, weight from density, vorticity confinement), a Gauss-Seidel projection with over-relaxation done directly on the face velocities, semi-Lagrangian advection of density, temperature and fuel (plus a uniform wind), self-advection, then burning, cooling and dissipation. Each side is a wall or open (outflow, clean air comes in). `FlipSim` is PIC/FLIP: particles move under gravity, are pushed apart, splat to the faces, the grid is projected with a density correction, and the change goes back to the particles (0.9 FLIP). Sparse cells count as air, so trapped air pockets collapse.
  - Presets are data (`FLUID_PRESETS`): canvas size, timing, ramp, emitter shape, rates, forces. `renderFluid` runs the sim at a fixed rate (gas 40 Hz, liquid 120 Hz), samples a frame every 1/fps s, downsamples a 2x grid, shades with Bayer 4x4 dithering on the ramp steps (transparency is the step below the first color, so edges dither out), and for loops simulates two cycles after a warm-up and crossfades the fields.
  - `fluid_tools.ts` is one tool, `fluid_fx`, with `apply` preview / layer / sprite. The layer path reuses `fxSchedule`, `placed`, `freeLayerName` and `fxPalette` from `fx_tools.ts`, so timing, cutting and palette append match `add_fx`; one `put_images` request carries the frames, palette and FX record.
  - Measured on an M-series Mac: a 64x64 grid x 48 frames renders in about 190 ms one-shot and 450 ms as a loop (two cycles plus warm-up); every preset at its default size renders in 110-230 ms.
- **Why:** the FX library's pixelfx smoke and fire are particle sprites; real flowing gas and water needed a solver. A MAC grid instead of Stam's collocated one makes the divergence the projection removes the same one tests measure, and lets the gas and liquid solvers share the layout. Crossfading fields rather than colors keeps the ramp and dither pattern intact across the seam. Ten Minute Physics has no license and PavelDoGreat's code is a WebGL shader pipeline, so nothing is copied.
- **Architecture:** a pure module (`sprite_fx/fluid.ts`, no document access) under a thin tool; no protocol or extension change. The FX record (`fluid:<preset>`, settings JSON in `render`) is not a library id, so `check_fx` checks the layer with its no-record rules (border, loop seam, colors) and export sees an ordinary effect layer. Semi-Lagrangian advection is not conservative: a swirl in a closed box keeps its smoke within a few percent, but strong buoyancy into a wall loses about 15%; presets open the sides the smoke leaves by.

## Effect pipelines and emitter extras (#107)
- **How:**
  - `sprite_fx/noise.ts`: seeded value, Perlin (2002), simplex and Worley noise in 2D, 3D and 4D, fBm, looping noise (4D on a circle) and `curl2`. Written from the papers; no library vendored.
  - `sprite_fx/pipeline.ts`: the pipeline schema, `runPipeline` (pure: one source image per frame in, palette-only frames out) and the step registry `STEP_TYPES` with 11 steps. Animated params are evaluated per frame by `paramsAt`. Steps reuse `juicePlan` and `warp` (juice), `darker` from `shading.ts` (selout outlines), `ditherToPalette` and the Bayer thresholds from `dither.ts`, and `nearest`/OKLab from `color.ts`. New pieces: grid and exact Euclidean distance transforms (outline thickness, glow) and `paletteStep` (one palette step lighter or darker).
  - `pipeline_tools.ts`: `fx_pipeline` previews, or writes in one `put_images` request. Over a layer it goes through `writeEffect`, which now takes an optional FX record; a blank canvas goes onto a new layer, with frames added as needed. The record has id `pipeline:<name>` and the pipeline JSON in `recipe`.
  - `fx/recipe.ts`: emitters take `shape` (line, ring, rect, path, outline), `aim`, `trail` and `curl`. With none of them the spawn draws stay the same, so old recipes render exactly as before. `fx_from_recipe` fills an outline shape's `points` from the named layer (`resolveOutlines`).
- **Why:** issue #107 asked for node-graph style effects without a node editor, plus the emitter features from research §5 (shapes, outlines, trails, curl noise).
- **Architecture:**
  - Steps work on full RGBA buffers at native resolution. One snap at the end keeps every pixel on the allowed colors, so a step may make in-between colors (tint, selout) and still writes only palette colors.
  - Dissolve ranks its noise over the opaque pixels, so `threshold` is exactly the fraction gone.
  - Trails and curl run inside each recipe run on the run's own clock, so loops still wrap.
  - smear (#105) and fluid (#106) become steps through `registerStep`; the schema and the tool description read the registry.
  - check_fx treats pipeline records as records it cannot re-render (edge checks only).
  - Re-applying a pipeline makes a second layer; delete the old one first.

## Juice and the sprite-effect core (#104)
- **How:**
  - `sprite_fx/curves.ts` has Penner's easings, a closed-form damped spring, a decaying bounce and a seeded shake.
  - `sprite_fx/raster.ts` has the pixel-safe warp and the hit flash. Rotations sample an 8x Scale2x upscale; other warps sample the source, and shrinks keep thin details (eyes, 1 px lines) found in their footprint. EPX rounds the corners of 1-2 px details, so scales through the upscale lost eyes.
  - `sprite_fx/juice.ts` turns an effect into one warp per frame. `juice_tools.ts` reads the layer, warps, and writes through `sprite_fx/write.ts`.
  - `put_images` items accept `hide_source` (protocol v36), so the copy layer and the hidden source land in one request.
- **Why:** the user bought CodeManu's FX tools and asked for the same kinds of effects built in, from public algorithms (research in `docs/fx-algorithms-research.md`). Juice comes first because smears and pipelines reuse its core.
- **Architecture:** every sprite effect writes a copy layer with the source hidden. Frames the effect does not touch hold a copy of the source, so hiding it changes nothing else. Scale2x copies existing pixels only, so transforms never add colors. RotSprite and Scale2x reference code is AGPL/GPL, so both are reimplemented from their descriptions.

## Walk check: near leg lighter than the far leg (#99)
- **How:** at each contact, `legLightness` takes the near leg's mean OKLab L (its mask, from the hip down) and the mean L of every other opaque composite pixel under the hip (the far leg). `judgeWalk` makes it an error when the near leg is less than `MIN_DEPTH` (0.12) lighter. It's skipped when there are fewer than 3 far-leg pixels (the far leg hidden). `walk_check` prints both values.
- **Why:** every benchmark run so far drew the legs in #3c3c5a (near) and #1d2b53 (far), ΔL 0.07. The judge read the arm against those legs as same-side in some runs and opposite in others (run 12 opposite, run 13 same-side, with the same leg colors). A pairing a judge gets right by chance isn't readable. A measured threshold turns that into a fix with a number. 0.12 lets a mid grey-violet near leg (#6a6a90, ΔL 0.24) against the navy pass.

## Motion review: does the walk read the way it is drawn (#99)
- **How:**
  - `motion_review` (`critic.ts`) measures the walk's contacts with `measureWalk`, the code `walk_check` uses, which now sits in `walk_check.ts` and is shared.
  - It shows a fresh critic only the two contact frames, side by side and enlarged on a checker, with the facing. The critic gets no measurement, layer names or brief.
  - The critic answers, per frame, the question a player answers: which arm it notices, which leg belongs to that arm's side, which way each points, what made it pair them, and whether it is sure (`parseMotion`).
  - `compareMotion` lists every finding with the fix (the same depth cue for the near arm and near leg). The findings are: an arm seen swinging with its paired leg; no pairing, or an unsure one; a pairing that differs from the measured near limbs.
  - Statuses: ok, readability, or errors (walk_check's measured errors come first). Critics can't call it (`AGENT_TOOLS` in `server.ts`).
- **Why:** after walk_check, the benchmark's walks were right by their layers, but the judge still saw the arm swing with the same-side leg: it took the dark far leg for the near one. A measurement can't see that; a viewer can. The first prompt asked which leg reads as near and said "usually the lighter one". That matched the agent's design, so Claude passed both runs that the judge failed. The prompt now asks how a player pairs the limbs, and whether every cue agrees. On run 11's contacts (dark near arm, light near leg), Claude answered same-side or unsure 3 times out of 3. With only the near arm recolored to a light step, it answered sure and correct 3 times out of 3. The animate skill now says to give the near arm and near leg the same depth cue.
- **Architecture:** a pure prompt and parser, a pure comparison, and one tool on the existing critic session and contact-sheet helpers. The animate skill runs it after walk_check says ok.

## Walk limb check: arms opposite legs, measured (#99)
- **How:**
  - `walk_check` (`walk_check.ts`, the tool in `animation_tools.ts`) reads the near arm and near leg on the walk's two contact frames. Each limb comes from a part layer, or from colors within rows (the arm above the hip, the leg below); layers named like "near arm" and "near leg" are found without naming them.
  - Only the part connected to the limb's top row counts, so the far arm's hand in the same color doesn't skew it. The hand's mean x over the bottom two rows minus the shoulder's over the top two rows (the foot against the hip for a leg) gives a signed offset toward the facing direction.
  - Errors: the arm and the leg on the same side at a contact, or a limb on the same side at both contacts. A limb that is missing or within 1 px of straight makes the verdict "unverifiable", never ok.
  - The limbs are stored in the pixel spec (`walk`), so a later call needs no arguments. The benchmark's new `walk_check` criterion runs it that way: an agent that never named the limbs fails it.
  - The animate skill makes it a gate: a walk isn't done until `walk_check` says ok, on the colored keys and again after the in-betweens.
- **Why:** two benchmark runs with the key-pose skill text scored motion 2 like the baseline. Both drew the whole cycle in one Lua call, and both judges saw the arm swing with the same-side leg while the agent's own table said the opposite. The unit test uses that run's frames 1 and 4. Codex's review chose this measurable check first. Its other two suggestions are still open: a stage gate in the extension (one tool can't enforce stages, since `execute_lua` bypasses any tool's refusal) and motion observations in the critic.
- **Architecture:** a pure measurement module (`limbMask`, `fromTop`, `readLimb`, `judgeWalk`) behind one tool; `pixel_spec` storage is reused; the benchmark adds a criterion type and calls the tool.

## FX recipes and the FX check (#72)
- **How:** `fx/recipe.ts` checks a JSON recipe with zod (`parseRecipe`: every problem by path) and compiles it into a pixelfx effect module whose `create` keeps "runs": a `Particles` system and `Lights` spawned at a cycle's start (emitter delays become the core's spawn delays; extra gravity and drag are applied to the run's own particles before each core step) plus rings (`Painter.ring`/`glowRing`), bands (core `band`) and shapes drawn from the run's own time in each phase's [start, end). Recording `render` lets the check re-render a flipped, turned or reseeded effect as placed (default records stay as before). The seam rule reads the sprite's frames rather than the effect, so it also catches frame timings that cut a loop mid-cycle; the colors rule counts RGB at any alpha, so soft library effects (smoke, fire) warn by design and a test pins that.
- **Architecture:** the engine stays pure (`fx/`), the recipe compiler sits beside the library and uses only the vendored core; tools reach Aseprite only through the document module. The wire grew two optional text fields on the existing FX record (Lua, the fake and `contract/put_images.json` agree; 16384 characters each).

## FX export: origin pivot, meta.fx, glow sheet (#71)
- **How:** `add_fx`, `fx_overlay` and `new_fx_sprite` record `{ id, x, y, fps, loop, windupMs }` (origin in sprite pixels; windup = `fxImpact` ms) as the layer property `aseprite-agent` `fx` through a new `fx` param on `put_images` and `create_animation` (protocol 30), reported as `get_state`'s layer `fx`. `export_for_engine` (`fxExport`) pivots a sprite of effects only on its top effect's origin (an explicit `pivot` wins, a character keeps bottom-center), writes non-default pivots on each JSON frame (Phaser reads `pivot`), adds `meta.fx` (fps, loop, windup, origin, hits as 0-based frames with `freeze_ms`) to the JSON every engine gets, and with light layers (not Normal, or `AI: fx … glow`) writes `<name>_glow.png` placed like the color sheet (`pack`'s `also` trims to both) while composing the color sheet from the other layers in the bridge (`composeNormal`); `glow: "baked"` keeps Aseprite's render. The fake now blends Addition layers at any opacity as drawSprite's new blend method does.
- **Why:** per-layer records let several effects share a sprite and vanish with their layer; the origin (not the placement anchor) is pixelfx's attach point, so the game places the effect like pixelfx does. Recording goes on the existing write so it stays one undo step. Composing in the bridge avoids a wire change to `snapshot` (hiding layers would modify the document); per-frame pivots only when asked or from an effect, so existing Phaser exports keep their origin. The new contract scenario pins the fake's Addition blend to Aseprite's pixels (it matched on the first run).
- **Architecture:** the wire grew one optional record param on two writes (Lua, the fake and `contract/put_images.json` agree); the export decision is pure (`fxExport`, `composeNormal`, `composeLight` in `export.ts` / `export_tools.ts`) over the document module. `fxImpact` moved to `fx_tools.ts` (re-exported by `fx_timing_tools.ts`) so the placing tools share it.

## FX palette cap only for indexed sprites (#70 live)
- **How:** `fxPalette` appends the effect's colors to an RGB sprite's palette even past 256 entries (Aseprite allows it). Only indexed sprites snap past 256. `SpriteInfo` now carries `colorMode`.
- **Why:** live tests ran with a full 256-entry default palette, so the effect was snapped to black and `check` failed. An RGB palette does not limit what pixels can hold.
- **Architecture:** the decision stays in `fx_tools.ts` (`fxPalette`). The document module only reports `colorMode`.

## FX overlay and hit-stop (#70)
- **How:** `fx_timing_tools.ts` adds `fx_overlay` and `hit_stop`. `overlayPlan` (pure) maps a tag or a start-frame range to effect times: each frame (or, retimed, each ~1000/fps part of it, durations split so they add up) shows the effect at its start time, offset so the effect's impact (`fxImpact`: the first pixelfx act hit, else the busiest frame) lands on `hit_frame`'s first moment; a one-shot past the range is cut (tag) or extended by linked frames (start frame). `anchor_layer` takes the layer's opaque bounds at the hit frame once (centre, or bottom centre for ground; melee defaults to ground). `hitStopPlan` makes the contact frame `freeze_ms - shake.ms` longer and inserts max(2, round(shake.ms / 33)) shake frames whose moved copies alternate sideways with amplitude round(amp * (n-1-i)/(n-1)), ending at 0, so the total grows by exactly `freeze_ms`; the flash is a snapshot turned white and written into the contact frame. Both send one `put_images` with the new `insert` (frames after `after`, cels linked by Aseprite's LinkCels or moved copies for `shift.layers`; covering tags grow, later tags and hits move), `durations` and `hit` params (protocol 29); `get_state` reports `celLinks` per layer and `fxHits`.
- **Why:** one request keeps one undo step; `apply_timeline_text` cannot insert frames in the middle and is a request of its own. Linked cels (not copies) keep the character editable in one place after retiming; a moved cel cannot share cel data (position is part of it), so shake frames are copies. The shake comes out of the freeze because the issue fixes the total at `freeze_ms`. A tag defaults to cut because it is the action's length. The hit lives in a sprite property (frames have no user data in Aseprite) and is shifted by later inserts, so #71's export reads frame numbers that still match (`SpriteInfo.hits`).
- **Architecture:** timing is pure bridge code over the document module; the wire only grew generic timeline edits on `put_images`, modelled in the fake (a linked cel is one cel object in several frames) and pinned by `contract/put_images.json` against Lua. Placement, palette and layer naming are shared with `add_fx` (`fxPalette`, `placed`, `freeLayerName`).

## FX follow-ups: anchor, palette, light layers in check (#69)
- **How:** `add_fx` takes `anchor`: `ground` puts pixelfx's `meta.origin` (the feet) at x, y; `center` puts the effect's visual centre there, `visualCenter` (`fx/index.ts`): the alpha-weighted centroid of the frame with the largest alpha sum, from a render at the effect's own fps with the same options, seed and canvas (cached in `fxAnchorPoint`, the helper later placers share). Each catalog entry has a default (`defaultAnchor`: melee centred, tags ground/prop/ambient mean ground, three hand-listed), shown by `list_fx` and `preview_fx`. By default the colors on the Normal effect layer are appended to the sprite palette through `put_images`' new `palette` param (protocol 28), in the same transaction; past 256 entries they are snapped to it instead (`snapToPalette` gained `minAlpha` so faint pixels snap too), and `new_fx_sprite` sets its palette to the effect's colors (median cut to 256 and snapped when more). `check` skips the per-pixel rules on layers that do not blend Normal and lists them as `checked.lightLayers`.
- **Why:** the origin is the ground point, so a hit spark "at" a point flashed 20 px above it; the busiest frame's centroid follows the flash, where the union of all frames would follow sparks that fly off. The palette is appended inside `put_images` to keep one undo step. A glow is light added over the art, so off-palette and semi-transparent findings on it were noise (a hit spark gave about 1800); on the color layer a hit spark now checks with 0 errors and a few orphan warnings (sparks), which stay.
- **Architecture:** anchoring is bridge-side data plus one pure function; the wire only grew an append list (Lua, the fake and `contract/put_images.json` agree). Indexed sprites now convert images through the sprite's own palette in `putOne` (`toIndexed`): `Image:drawImage` maps through Aseprite's current palette, which misses entries added earlier in the same transaction.

## FX library and tools: list, preview, add (#69)
- **How:** 42 pixelfx effects are vendored as-is per category; `fx/library.ts` catalogs them from their own meta, and `fx_tools.ts` offers `list_fx`, `preview_fx` (contact sheet from `image.ts` `contactSheet`), `add_fx` and `new_fx_sprite`. `add_fx` maps sprite frames to effect times by their durations (`fxSchedule`; loops wrap), renders at those times (`renderFx` `times`, `canvas`, and `color` without light) and sends one `put_images` request (protocol 27): it adds frames (copies of the last frame), writes `AI: fx <id>` and its Addition glow layer (`blend_mode`, also on `put_image`), all in one transaction. get_state reports `blendMode`.
- **Why:** one request is the only way to get one undo step across many cels and new frames (each request is its own transaction and step capture; tools never write Lua), and it keeps the fake honest through the contract suite (`contract/put_images.json`). Effects that read the character (`onBody`), text effects four one-shots that do not end empty and a few large ones were left out; the melee effects' `actor: 2` is gallery-only, so the catalog drops it.
- **Architecture:** the engine stays pure (`fx/`); the catalog is data over the vendored modules; the tools reach Aseprite only through the document module (`putImages`). The fake refuses snapshots that would need non-normal blending instead of compositing them differently.

## Pixel FX engine: vendored pixelfx behind renderFx (#68)
- **How:** pixelfx's core JS (pinned commit, MIT) is copied as-is into `bridge/src/fx/vendor/` and built with `allowJs` (`checkJs` off). `fx/index.ts` exports `renderFx`, which steps an effect module on a fixed 120 Hz clock (step j ends at exactly j / 120 s), samples it at the requested fps and returns baked frames, the light buffer as `glow`, and an optional palette snap through `snapToPalette`.
- **Why:** vendoring keeps upstream behaviour exact and makes upgrades a reviewed diff; a hand port would drift. The exact clock makes 30 and 60 fps renders identical at shared times and makes a loop's frame at t = duration equal its frame at 0. Rig, actor, act, scene and font are cut (`NOTICE.md` lists the edits); text and actor effects throw.
- **Architecture:** a pure module with no document or wire access: only `index.ts` and its declarations (`vendor/core/index.d.ts`) are typed; our code stays strict. Three effects are vendored as the test set; the effect library and tools come later (#69).

## Refactor wave 3: tests that keep fakes honest (#86)
- **How:** the contract suite (`tests/contract/*.json`) replays the same wire requests against `fake_document.mjs` and the Lua handlers. `eval_live.mjs` runs the skill evals in Aseprite. Live tests split hard checks from soft checks (`soft()`). `npm run gen` is the single generator, and the Lua-tests stamp warns when the extension changed without a Lua run. The ACP fake's permission requests are checked against fixtures from the real agents.
- **Why:** before, the fake and Lua drifted silently, and model variance failed live tests. The contract work found six Lua bugs: tilemap snapshots, `mirror_frames` tags, hidden groups, swatch layers, palette case and `create_animation` leaks.
- **Architecture:** the document has two adapters (the fake and Lua) behind one contract, and tests are the seam. Evals are written once and run on both adapters.
